# Начисление оплаты тренеру за занятие

Дата: 2026-10-29. Статус: согласовано, реализовано и проверено на stage 2026-10-29; ядро не изменялось.

## Требования

- Оплата группового занятия зависит от числа **фактически пришедших** участников.
- Каждая ступень для 1, 2, 3 и 4 участников настраивается отдельно, включая полную группу. 1500 ₽ за четверых — пример, а не константа.
- Пропорционального расчёта между ступенями нет. Конкретные суммы пользователь уточнит.
- Проведённое занятие сохраняет отдельную затрату на тренера, доступную в реестре начислений.

## Исходное состояние до реализации

- В `ClassSession` есть `trainerCompensation`, `attendedCount` и `completionLockedAt`.
- Отдельного справочника тренеров, тарифов и реестра начислений в приложении нет.
- `Booking` различает `ATTENDED`, `NO_SHOW`, `LATE_CANCEL` и отмены. Списание посещения и фактическое присутствие — разные признаки.
- `record-past-attendance-handler.ts` создаёт занятие со статусом `COMPLETED` и добавляет посещения по одному. Можно передать `existingClassSessionId` и добавить клиента в существующее занятие.
- `record-split-attendance-handler.ts` отдельно проводит посещение пары. Начисление должно учитывать этот сценарий, но ставки сплитов и персональных занятий ещё не определены.
- `CoreApiClient` не предоставляет общей транзакции для нескольких записей CRM. Безопасное закрытие требует восстановления после частичного сбоя и защиты от конкурирующих команд.

## Настройка тарифов

Предлагается справочник «Тарифы оплаты тренеров». В карточке тарифа:

| Поле | Назначение |
| --- | --- |
| Название | Например, «Группа — основной тариф» |
| Формат | Группа; другие форматы подключаются с отдельными правилами |
| Версия | Неизменяемая опубликованная версия тарифа |
| Действует с / по | Выбор по дате начала занятия, а не по дате внесения в CRM |
| Статус | Черновик / опубликован / архив |
| 1 участник | Настраиваемая сумма в рублях |
| 2 участника | Настраиваемая сумма в рублях |
| 3 участника | Настраиваемая сумма в рублях |
| 4 участника | Настраиваемая сумма в рублях |

Для текущей вместимости четыре отдельных денежных поля проще отдельной таблицы диапазонов: нет пересекающихся интервалов и пропущенных границ. При расширении вместимости модель можно расширить. Все суммы хранятся в штатном денежном формате Twenty (`amountMicros`, `currencyCode`), расчёт — целочисленный.

Черновик может быть заполнен частично. Публикация требует всех четырёх сумм; каждая неотрицательна. Явно заданный ноль допустим, пустое значение не означает ноль. Известные сейчас суммы не заполняются автоматически примером 1500 ₽.

Опубликованная версия не редактируется. Изменение ставок создаёт новую версию с датой действия. Нельзя допускать неоднозначный выбор из нескольких действующих назначений тарифа.

Добавляется справочник «Тренеры» с именем и признаком активности. У занятия обязательно указывается фактический тренер перед начислением. Для постоянной группы можно задать тренера по умолчанию, но замена сохраняется на конкретном занятии.

Назначение тарифа связывает тренера, формат, версию тарифа и период применения. Несколько тренеров могут использовать одну версию. Это позволяет менять ставки конкретного тренера, не копируя условия в каждую тренировку.

## Как считать участников

Основание — записи `Booking` конкретного занятия со статусом `ATTENDED`. Участников считать по уникальным клиентам; дубли записей одного клиента блокируют закрытие и требуют исправления.

`NO_SHOW`, `LATE_CANCEL`, отмены и оставшиеся `BOOKED` не входят в число посетивших. Даже если у пропустившего клиента списалось посещение, он не увеличивает оплату тренеру. Отработка с фактическим присутствием учитывается независимо от способа оплаты.

Перед закрытием у всех записей должен быть окончательный статус; оставшиеся `BOOKED` требуют отметки посещения или пропуска. `attendedCount` — отображаемый счётчик, а не самостоятельное основание начисления.

Для 1–4 участников берётся ровно соответствующая ступень. При превышении вместимости или отсутствии ставки закрытие блокируется. Оплата за ноль участников требует отдельного бизнес-решения; до него автоматическое начисление для такого случая блокируется. Отменённое студией занятие не создаёт обычное начисление за проведение.

## Когда фиксировать затрату

Единица начисления — **одно занятие одного тренера**, а не списание посещения у одного клиента. Четыре клиента на группе дают четыре клиентских посещения и одну общую затрату на тренера.

Предлагается действие «Закрыть занятие» после окончания тренировки:

1. Проверить фактического тренера, время, формат и итоговые статусы участников.
2. Перечитать состав занятия и найти единственный подходящий тариф на дату начала.
3. Показать предпросмотр: тренер, дата, число посетивших, версия тарифа, выбранная ступень и сумма.
4. При подтверждении заново проверить данные: изменение состава или тарифа требует нового предпросмотра.
5. Создать исходное начисление в реестре и сохранить снимок расчёта.
6. Обновить `trainerCompensation` из реестра и установить `completionLockedAt` только после успешного завершения операции.

До закрытия можно показывать предварительную сумму. Статус `COMPLETED` сам по себе не означает завершённый расчёт зарплаты: текущая команда выставляет его уже при внесении первого посещения.

После закрытия изменение тренера, даты, формата и состава проводится только командой исправления с перерасчётом. Обычные формы и команды посещения должны проверять блокировку. Если списания уже внесены, но начисление ещё не зафиксировано, занятие видно в списке «Проведены — не начислено».

При заднем внесении группового занятия все клиенты должны ссылаться на общий `ClassSession`. Нельзя автоматически создавать отдельный слот для каждого клиента и начислять каждому слоту полную оплату. UI должен предлагать выбор существующего занятия; совпадение только по времени недостаточно для автоматического объединения.

## Реестр «Начисления тренерам»

Источник истины — отдельный журнал денежных операций. Поле `trainerCompensation` занятия отображает сумму операций по этому занятию и не редактируется вручную.

| Данные записи | Для чего сохраняются |
| --- | --- |
| Занятие и тренер | Связь затраты с конкретной работой и получателем |
| Дата занятия | Отнесение затраты к периоду проведения |
| Дата записи и автор | Аудит внесения, включая заднее число |
| Тип операции | Начисление / сторно |
| Сумма и валюта | Денежная затрата; сторно имеет отрицательную сумму |
| Версия тарифа | Источник применённых условий |
| Снимок расчёта | Формат, число участников, список учтённых записей и клиентов, выбранная ступень и её сумма |
| Ссылка на исходную операцию | Трассировка сторно и заменяющего начисления |
| Причина | Обязательна для исправлений |
| Ключ операции и ревизия | Защита от повторного начисления |

Историческая сумма и снимок неизменяемы. Новые тарифы не пересчитывают старые начисления. Исправление создаёт сторно исходной суммы и новое начисление с новым снимком. При замене тренера сторно относится к прежнему тренеру, новое начисление — к фактическому.

Отчёты: начислено по тренеру за период, детализация по занятиям, затраты по форматам и список занятий без начисления. Итог учитывает сторно; несколько записей исправления не увеличивают число проведённых занятий.

Начисление фиксирует расход и обязательство перед тренером. Учёт фактических выплат — отдельный следующий контур; до его появления отчёт показывает «начислено», а не «остаток к выплате».

## Целостность и доступ

- Уникальность исходного начисления по занятию обеспечивается индексом, а не только проверкой перед созданием. Для MVP у занятия один тренер.
- Повтор закрытия с новым ключом запроса тоже не создаёт второй расход: защита привязана к занятию и ревизии.
- Для исправления уникальны сторно исходной операции и заменяющее начисление соответствующей ревизии.
- Начисление и блокировка состава должны согласовываться через транзакционную серверную команду либо доказанный механизм сериализации по занятию. Один `completionLockedAt` не защищает от гонки.
- Если используется возобновляемая последовательность CRM-мутаций, нужен сохранённый контекст операции. Повтор дозавершает исходный снимок, а не пересчитывает сумму по изменившимся данным. Частичный результат явно виден и не считается закрытым занятием.
- Оператор не редактирует денежный журнал, снимок расчёта, кэш суммы и опубликованные тарифы через обычный CRUD. Ставки меняет уполномоченный администратор; исправления имеют автора и причину.
- Старые занятия не начисляются автоматически по сегодняшним ставкам. Нужен отдельный предпросмотр исторических данных и решение по периоду начала учёта.

## Реализация и проверка

1. Добавить тренеров, версии тарифов, назначения, журнал и связи с занятием; настроить роли и индексы.
2. Реализовать выбор тарифа на дату занятия и расчёт по фактическим участникам. Суммы всех четырёх ступеней заполняются в CRM.
3. Добавить команду закрытия с предпросмотром, защитой от конкуренции и восстановлением после сбоев; подключить проверки закрытия в существующие команды посещения, включая сплиты.
4. Добавить команду исправления со сторно и новым начислением.
5. Вывести настройки, реестр, сумму в карточке занятия и список неначисленных проведённых занятий.
6. Проверить на staging после реализации и просмотра app plan.

Поведенческие проверки:

- Для 1, 2, 3 и 4 посетивших применяются четыре независимо настроенные суммы; изменение четвёртой ступени влияет на новые начисления.
- Три посетивших и один платный пропуск дают ставку за троих.
- Четыре клиентских списания в одном занятии дают одно исходное начисление.
- Незавершённые отметки участников, отсутствие тренера, ставки или неоднозначное назначение блокируют закрытие с понятной ошибкой.
- Новая версия тарифа не меняет закрытую историю; заднее внесение выбирает ставку по дате занятия.
- Повтор команды и два одновременных закрытия не удваивают затрату.
- Сбой после записи в журнал, но до обновления занятия восстанавливается без второго начисления.
- Исправление состава или тренера сохраняет исходную историю и корректный итог после сторно.
- Сплит не получает два начисления из-за двух клиентских записей; его тариф настраивается отдельно до включения расчёта для этого формата.

## Оставшиеся бизнес-решения

- Значения всех четырёх групповых ступеней.
- Правило оплаты при нуле посетивших, если тренер приехал, но никто не пришёл.
- Ставки персональных и сплит-занятий, если они входят в первый выпуск.
- Дата начала учёта и необходимость переноса старых занятий в реестр.

## Фактическая реализация

Добавлены `StudioTrainer`, `TrainerPayRate`, `TrainerRateAssignment`, `TrainerPayEntry` и служебный `StudioSessionLock`. Реализованы публикация снимка тарифа, предпросмотр, закрытие, исправление через сторно, восстановление после сбоя, отчёт за период и представления незавершённых начислений/незакрытых занятий. Полный снимок включает записи всех участников и связанные операции пакетов.

Закрытие и существующие команды изменения состава сериализуются уникальной блокировкой на занятие. У блокировки нет автоматического истечения. Исправление факта присутствия поддерживает переходы между `ATTENDED`, `NO_SHOW`, `LATE_CANCEL`, сохраняя клиентское списание.

Командные ограничения не заменяют права прямого CRUD в workspace. Отдельное разграничение HTTP-доступа для публикации тарифов и закрытия пока не реализовано; аутентификация обязательна, рабочее использование рассчитано на доверенных сотрудников. Суммы, ставки других форматов, нулевое посещение, начало учёта и права пользователей workspace требуют настройки перед выпуском.

Операторский порядок и ограничения: [Оплата тренеров](instructions/trainer-compensation.ru.md).
