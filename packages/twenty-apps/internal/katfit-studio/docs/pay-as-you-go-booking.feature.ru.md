# ТЗ: запись на занятие с оплатой по факту

## 1. Цель

Дать администратору возможность забронировать клиенту место на будущем
занятии, когда клиент не использует пакет и оплачивает посещение после
проведения занятия. Бронь должна занимать место в расписании, но не списывать
посещение из пакета. Неоплаченная услуга должна быть видна в разделе оплат.

Функционал распространяется на разовые групповые занятия и персональные
тренировки.

## 2. Роли и термины

- **Администратор** — создаёт занятие, добавляет в него клиентов и фиксирует
  оплату.
- **Бронь** — запись клиента на конкретный слот занятия.
- **Ожидаемая оплата** — финансовая обязанность клиента со статусом
  `EXPECTED`; это не подтверждённый денежный платёж.
- **Оплата по факту** — способ записи, при котором оплата создаётся в статусе
  ожидания и подтверждается только после проведённого занятия.

## 3. Основной сценарий

1. Администратор создаёт новый будущий слот или открывает существующий.
2. В диалоге «Добавить клиента» выбирает способ записи:
   - «По пакету»;
   - «Оплата по факту».
3. Для «Оплаты по факту» администратор выбирает активную услугу нужного
   формата:
   - разовую групповую услугу (`SINGLE`);
   - персональную услугу (`PERSONAL`).
4. Администратор выбирает одного или нескольких клиентов и добавляет их в
   слот.
5. Система создаёт бронь и ожидаемую оплату, занимает место в слоте и выводит
   рядом с клиентом отметку «оплата ожидается».
6. После проведения занятия бронь переводится в `ATTENDED`. Администратор
   подтверждает оплату с указанием способа оплаты, времени и, при наличии,
   номера чека.

## 4. Правила записи

### 4.1. Запись по пакету

- Доступна только клиенту с активным пакетом подходящего формата и с доступным
  остатком посещений.
- При создании брони резервируется одно посещение.
- Для такой брони `paymentStatus = NOT_REQUIRED`.
- Ожидаемая оплата не создаётся.

### 4.2. Запись с оплатой по факту

- Не требует пакета у клиента.
- Доступна только для активной услуги категорий `SINGLE` или `PERSONAL`.
- Формат услуги обязан совпадать с форматом слота.
- Слот должен иметь статус `PLANNED` или `CONFIRMED`, начинаться в будущем и
  иметь свободное место.
- При сохранении создаются:
  - `StudioBooking` со статусом `BOOKED`, без списания посещения и с
    `paymentStatus = EXPECTED`;
  - `StudioPayment` со статусом `EXPECTED`, суммой, равной цене выбранной
    услуги на момент записи, и привязкой к клиенту.
- Одна бронь увеличивает `bookedCount` слота на единицу.
- У одного слота могут одновременно быть участники по пакету и с оплатой по
  факту.

### 4.3. Переключение способа записи

- Переключение «По пакету» / «Оплата по факту» не сбрасывает выбранных в
  диалоге клиентов.
- Оно влияет только на клиентов, которых администратор добавит следующим
  действием «Добавить выбранных».
- Участники, уже добавленные в черновик нового занятия, сохраняют выбранный
  для них способ записи.

## 5. Статусы

| Сущность | Статус | Значение |
| --- | --- | --- |
| Бронь | `NOT_REQUIRED` | Оплата отдельным платёжным обязательством не требуется: запись по пакету. |
| Бронь | `EXPECTED` | Оплата по факту ожидается. |
| Бронь | `PAID` | Ожидаемая оплата подтверждена. |
| Бронь | `WAIVED` | Ожидаемая оплата снята из-за отмены занятия. |
| Оплата | `EXPECTED` | Долг к оплате. |
| Оплата | `PAID` | Деньги приняты и реквизиты сохранены. |
| Оплата | `FAILED` | Ожидаемая оплата закрыта без приёма денег из-за отмены. |

## 6. Отображение задолженности

В объекте «Оплаты» должен быть вид «К оплате».

- Фильтр вида: `Payment.status = EXPECTED`.
- В строке отображаются название, клиент и сумма.
- Оплаты со статусами `PAID`, `FAILED`, `REFUNDED` и
  `PARTIALLY_REFUNDED` в этот вид не входят.
- В расписании участник с `Booking.paymentStatus = EXPECTED` помечается как
  «оплата ожидается».

Для совместимости с метаданными CRM дополнительные relation-поля между
оплатой, бронью и услугой не требуются. Техническая ссылка брони хранится в
существующем поле `Payment.externalId` с префиксом `pay-as-you-go:`; название
услуги входит в название ожидаемой оплаты.

## 7. Подтверждение оплаты

Подтверждение доступно только при одновременном выполнении условий:

- бронь имеет статус посещения `ATTENDED`;
- `Booking.paymentStatus = EXPECTED`;
- соответствующая оплата имеет `Payment.status = EXPECTED`.

При подтверждении система:

1. переводит оплату в `PAID`;
2. сохраняет `paymentMethod`, `paidAt` и необязательный `fiscalReceiptId`;
3. переводит `Booking.paymentStatus` в `PAID`;
4. записывает событие `PAYMENT_CONFIRMED` в журнал событий студии.

Повторный запрос подтверждения должен быть идемпотентным: вторая оплата не
создаётся и сумма не меняется.

## 8. Отмена занятия

При отмене будущего слота:

- пакетные брони отменяются по действующим правилам, резерв посещения
  освобождается;
- бронь с оплатой по факту получает `CANCELLED_BY_STUDIO` и
  `paymentStatus = WAIVED`;
- соответствующая ожидаемая оплата получает `FAILED`;
- `bookedCount` слота становится равным нулю.

Подтверждённая оплата автоматически не возвращается: возврат остаётся
отдельной финансовой операцией.

## 9. Журнал событий

Должны фиксироваться как минимум следующие события:

- `SESSION_CREATED` — создан новый слот занятия;
- `BOOKING_CREATED` — создана бронь;
- `BOOKING_CANCELLED` — бронь отменена;
- `PAYMENT_CONFIRMED` — ожидаемая оплата подтверждена;
- `OPERATION_FAILED` — бизнес-операция не выполнена.

Ошибка записи аудита не должна отменять уже успешно выполненную бизнес-
операцию.

## 10. API-контракты

### Создание записи по факту

`POST /studio/bookings/create-pay-as-you-go`

Тело: `personId`, `productId`, `classSessionId`, `idempotencyKey`.

Успех: `200`, идентификаторы брони и оплаты. Ошибки: неверный ввод, отсутствие
слота, неподходящая услуга, прошедший или заполненный слот.

### Подтверждение оплаты

`POST /studio/bookings/confirm-pay-as-you-go-payment`

Тело: `bookingId`, `paymentMethod`, опционально `paidAt`, `fiscalReceiptId`.

### Отмена записи по факту

`POST /studio/bookings/cancel-pay-as-you-go`

Тело: `bookingId`, `cancelledAt`, `idempotencyKey`.

## 11. Критерии приёмки

1. Клиента без пакета можно добавить в будущий подходящий слот с оплатой по
   факту.
2. При этом не изменяется остаток посещений ни одного пакета.
3. Создаются ровно одна бронь и одна ожидаемая оплата; вместимость меняется на
   единицу.
4. В «Оплаты → К оплате» видна ожидаемая оплата без ошибок загрузки страницы.
5. Переключение способа записи не очищает выбранных клиентов.
6. Нельзя создать запись по факту в прошлом, отменённом или заполненном слоте
   либо с услугой другого формата.
7. До статуса `ATTENDED` подтверждение оплаты отклоняется.
8. После подтверждения оплата и бронь получают статус `PAID`.
9. При отмене будущего занятия неоплаченная обязанность закрывается и не
   остаётся в виде «К оплате».
10. В журнале есть события создания занятия, брони и подтверждения оплаты.
