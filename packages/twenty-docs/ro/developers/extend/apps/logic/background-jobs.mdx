## Prezentare generală

O rulare a unei funcții de logică este limitată de `timeoutSeconds` (maximum 900 de secunde). Orice lucru care nu poate fi finalizat în acel interval — o resincronizare completă, un fan-out per înregistrare, un API de la o terță parte care aplică limitare de rată — trebuie împărțit în execuții mai mici.

`enqueueJobs` face exact asta: le cere lucrătorilor Twenty să ruleze mai târziu una dintre funcțiile de logică ale aplicației tale, o dată pentru fiecare payload, fiecare rulare în propriul său proces, cu propriul său buget de timeout. Apelantul returnează imediat.

```text
  ┌─────────────────┐  enqueueJobs(...)  ┌──────────────┐   ┌────────────────────┐
  │ Logic function  │ ─────────────────▶ │ Job queue    │──▶│ Logic function     │
  │ (returns now)   │                    │ (workers)    │   │ (fresh run/timeout)│
  └─────────────────┘                    └──────────────┘   └────────────────────┘
```

## Pune rulările în coadă

Importă `enqueueJobs` din `twenty-sdk/logic-function`, indică-l către `universalIdentifier` al funcției logice de rulat și transmite câte un payload pentru fiecare rulare funcției enqueue.

```ts src/logic-functions/sync-all-contacts.ts
import { enqueueJobs } from 'twenty-sdk/logic-function';

await enqueueJobs({
  logicFunctionUniversalIdentifier: '9f1c3d7e-51b8-4a29-8f0d-7c4e2a6b1d33',
  jobs: [{ payload: { page: 1 } }],
});
```

Fiecare rulare primește payloadul său ca argument al handlerului, exact ca orice alt declanșator. Ținta trebuie să aparțină **aceleiași aplicații** ca apelantul — punerea în coadă a funcției altei aplicații este respinsă cu `Logic function not found` și nu se pune nimic în coadă. Un singur apel acceptă până la `200` joburi.

<Note>
`enqueueJobs` revine imediat ce joburile sunt acceptate, nu când au fost rulate. Nu întoarce rezultatele țintelor — fă ca fiecare țintă să scrie ce produce în [magazinul cheie-valoare](/ro/developers/extend/apps/logic/key-value-store) sau într-o înregistrare din spațiul de lucru dacă trebuie să le citești ulterior. Pentru a afla dacă o execuție s-a încheiat, interogați periodic [starea jobului](#poll-jobs).
</Note>

<Note>
Ajutorul mai vechi `enqueueJob`, care pune în coadă un singur job per apel, este depreciat. Folosiți în schimb `enqueueJobs` cu o listă `jobs` cu un singur element. Argumentul `payloads` este și el învechit — transmiteți în schimb `jobs`, care acceptă aceeași încărcătură utilă pentru fiecare execuție și vă permite să denumiți fiecare execuție. Câmpul `jobIds` al rezultatului este, de asemenea, învechit: citiți fiecare id din `jobs` în schimb.
</Note>

## Interogați periodic joburile

`enqueueJobs` returnează câte o intrare pentru fiecare rulare pusă în coadă în `jobs`, fiecare având propriul `jobId`, în aceeași ordine ca joburile pe care le-ați transmis. `getJobs` citește stadiul la care au ajuns acele execuții, într-un singur apel.

```ts
import { enqueueJobs, getJobs } from 'twenty-sdk/logic-function';

const { jobs } = await enqueueJobs({
  logicFunctionUniversalIdentifier: ENRICH_COMPANY,
  jobs: [{ payload: { companyId: 'abc' } }],
});

const statuses = await getJobs(jobs.map(({ jobId }) => jobId));
```

Un singur apel `getJobs` citește cel mult `200` de ID-uri, aceeași limită pe care `enqueueJobs` o aplică unui lot.

Fiecare intrare conține ID-ul solicitat:

| Câmp           | Ce conține                                                                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `jobId`        | ID-ul interogat.                                                                                                                                                           |
| `state`        | `WAITING`, `PRIORITIZED`, `DELAYED`, `ACTIVE`, `WAITING_CHILDREN`, `COMPLETED` sau `FAILED`.                                                                               |
| `attemptsMade` | Încercările din coadă efectuate până acum, inclusiv cea curentă.                                                                                                           |
| `failedReason` | Mesajul de eroare al ultimei încercări eșuate sau, în caz contrar, `null`.                                                                                                 |
| `enqueuedAt`   | Momentul în care lucrarea a fost acceptată, în milisecunde epoch.                                                                                                          |
| `scheduledAt`  | Momentul în care sarcina a devenit pentru prima dată eligibilă pentru rulare, în milisecunde epoch. Consultați [Când este programată o sarcină](#when-a-job-is-scheduled). |
| `startedAt`    | Momentul în care un lucrător a preluat-o; `null` cât timp încă așteaptă.                                                                                                   |
| `finishedAt`   | Momentul în care s-a finalizat sau a eșuat; `null` cât timp încă rulează.                                                                                                  |

O lucrare care nu a fost încă preluată apare în mod normal ca `PRIORITIZED`, nu ca `WAITING`, deoarece lucrările aplicației sunt puse în coadă la o prioritate mică fixă. `COMPLETED` și `FAILED` sunt stările terminale. O buclă de interogare ar trebui, de asemenea, să renunțe singură după un număr limitat de încercări, în loc să aștepte la nesfârșit, deoarece o execuție poate fi citită doar cât timp coada o păstrează: 4 ore după finalizare, 7 zile după eșec și, în ambele cazuri, doar cele mai recente 1000 de lucrări în acea stare.

`getJobs` returnează numai lucrările pe care încă le păstrează, astfel încât un ID care a fost eliminat — sau nu a existat niciodată — pur și simplu lipsește din rezultat, în loc să provoace o eroare pentru întregul lot. Compară ceea ce primești înapoi cu ceea ce ai solicitat pentru a le identifica și tratează un ID lipsă ca „nu mai este cunoscut”, ceea ce nu este același răspuns ca „nu a rulat niciodată”.

Stările sunt limitate la spațiul de lucru din care se efectuează apelul, astfel încât un spațiu de lucru nu poate citi niciodată lucrarea altui spațiu de lucru.

## Alege propriul ID al lucrării

Transmite `jobs` în loc de `payloads` pentru a denumi tu însuți fiecare execuție. ID-ul pe care îl transmiți este cel pe care îl acceptă `getJobs`, astfel încât un apelant poate interoga o lucrare fără a fi nevoit să stocheze ceea ce a returnat `enqueueJobs`.

```ts
await enqueueJobs({
  logicFunctionUniversalIdentifier: ENRICH_COMPANY,
  jobs: [{ payload: { companyId: 'abc' }, jobId: 'enrich-abc' }],
});
```

Un ID are cel mult 128 de caractere: litere, cifre, `_`, `.` sau `-`, iar două lucrări dintr-un singur apel nu pot avea același ID. Transmite fie `payloads`, fie `jobs`, niciodată ambele. Când omiți `jobId`, Twenty generează unul.

Un `jobId` este, de asemenea, o cheie de idempotență: punerea în coadă a unui ID pe care coada îl păstrează încă este acceptată, dar **nu** pornește o a doua execuție, iar `getJobs` continuă să raporteze prima execuție. Astfel, reîncercarea punerii în coadă este sigură. Două avertismente: garanția durează numai cât timp lucrarea este păstrată, astfel încât același ID poate porni o execuție nouă după ce cea originală a fost eliminată, iar ID-urile sunt partajate de fiecare aplicație dintr-un spațiu de lucru, așa că adaugă un prefix ID-urilor tale dacă o coliziune ar conta.

## Opțiuni job

Opțiunile se aplică fiecărei rulări din lot.

| Opțiune      | Implicit | Interval                                   | Ce face                                                                                                                                                                                           |
| ------------ | -------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `retryLimit` | `0`      | `0`–`10`                                   | Numărul total de încercări suplimentare în coadă. Reîncercările solicitate de aplicație sunt limitate la `3`. Crește această valoare numai pentru handleri care sunt siguri de rulat de două ori. |
| `delayMs`    | `0`      | `0`–`604800000` (7 zile)                   | Așteaptă atât timp înainte ca rulările să devină eligibile.                                                                                                                                       |
| `limiter`    | niciunul | `durationMs / max` între `100` ms și 1 oră | Distanțați uniform execuțiile, cel mult `max` per `durationMs`. Consultați [Ritmați execuțiile cu un limitator](#pace-runs-with-a-limiter). Nu poate fi combinat cu `delayMs`.                    |

```ts
await enqueueJobs({
  logicFunctionUniversalIdentifier: '9f1c3d7e-51b8-4a29-8f0d-7c4e2a6b1d33',
  jobs: [{ payload: { page: 1 } }],
  retryLimit: 3,
  delayMs: 60_000,
});
```

Pentru a seta limita de reîncercări o singură dată pentru fiecare rulare pusă în coadă a unei funcții, declarați `retryLimit` chiar pe funcție. Se aplică rulărilor pornite de `enqueueJobs`, cron, evenimentele bazei de date și rutele serverului, iar un `retryLimit` transmis către `enqueueJobs` îl suprascrie pentru acel apel. Fără aceasta, valorile implicite sunt `0` pentru `enqueueJobs`, `10` pentru cron și `3` pentru evenimentele bazei de date și rutele serverului.

```ts
export default defineLogicFunction({
  universalIdentifier: '9f1c3d7e-51b8-4a29-8f0d-7c4e2a6b1d33',
  retryLimit: 3,
  handler,
});
```

## Ritmați execuțiile cu un limitator

Transmiteți `limiter: { max, durationMs }` pentru a distanța execuțiile unui apel la intervale de `durationMs / max`, de exemplu pentru a rămâne sub limita de rată a unei terțe părți.

```ts
await enqueueJobs({
  logicFunctionUniversalIdentifier: ENRICH_COMPANY,
  jobs: companies.map((company) => ({ payload: { companyId: company.id } })),
  limiter: { max: 10, durationMs: 60_000 },
});
```

Aici, o execuție devine eligibilă la fiecare 6 secunde. Cum funcționează:

* Apelurile pentru aceeași funcție din același spațiu de lucru, cu aceleași valori pentru `max` și `durationMs`, partajează o singură planificare, astfel încât un al doilea apel continuă după execuțiile rezervate de primul. Modificarea oricăreia dintre valori pornește o planificare separată.
* Fiecărei execuții i se atribuie următorul slot liber sau momentul actual dacă planificarea este inactivă, iar următorul slot se mută cu un interval mai târziu. Execuțiile sunt distanțate uniform, niciodată în rafale.
* Nu există un orizont: un lot mare poate fi planificat cu zile în avans. Se aplică în continuare limitele obișnuite de [memorie a cozii](#queue-memory), iar o acumulare mare își păstrează memoria până când se golește.
* `max` și `durationMs` trebuie să fie numere întregi pozitive, cu un interval între `100` ms și 1 oră. Combinarea `limiter` cu `delayMs`, chiar și `delayMs: 0`, este respinsă cu `INVALID_INPUT` și nu se pune nimic în coadă.
* Sunt ritmate doar execuțiile apelurilor care transmit `limiter`. Reîncercările își păstrează propria temporizare progresivă, iar execuțiile pornite de cron, evenimente de bază de date, `onConnect` sau rute de server nu sunt ritmate.
* Repunerea în coadă a unui `jobId` pe care coada îl păstrează încă nu ocupă un alt slot.
* Limitatorul distanțează momentele în care execuțiile devin eligibile. Nu limitează câte execuții rulează în același timp, iar o execuție poate începe mai târziu decât slotul său atunci când lucrătorii sunt ocupați.
* Dacă ritmarea nu este disponibilă din cauza unei defecțiuni tehnice, execuțiile sunt puse în coadă fără ritmare, în loc să fie refuzate.

## Când este planificată o sarcină

Fiecare intrare din `jobs` returnată de `enqueueJobs` și fiecare stare returnată de `getJobs` conține `scheduledAt`: momentul în care sarcina a devenit pentru prima dată eligibilă pentru execuție, în milisecunde epoch.

| Sarcina a fost pusă în coadă | `scheduledAt`                                        |
| ---------------------------- | ---------------------------------------------------- |
| Cu un `limiter`              | Slotul care i-a fost atribuit.                       |
| Cu `delayMs`                 | Momentul în care a fost acceptată, plus întârzierea. |
| În caz contrar               | Momentul în care a fost acceptată.                   |

Este stabilit o singură dată, când sarcina este acceptată, și nu se modifică niciodată ulterior, inclusiv între reîncercări. Punerea în coadă a unui `jobId` pe care coada îl păstrează încă raportează `scheduledAt` al sarcinii existente. Odată ce sarcina a fost eliminată, o sarcină nouă cu același id primește unul nou.

`scheduledAt` nu este o predicție a momentului în care începe sarcina: comparați-l cu `startedAt` pentru a vedea cât timp a așteptat un lucrător.

<Note>
**Prioritatea nu este încă configurabilă.** Joburile puse în coadă rulează întotdeauna cu cea mai joasă prioritate, astfel încât activitatea platformei să nu fie niciodată întârziată de joburile aplicației. Controlul asupra priorității va fi disponibil în curând.
</Note>

Rularea pusă în coadă moștenește utilizatorul activ al funcției care a pus-o în coadă, astfel încât acționează cu aceleași permisiuni.

## Memoria cozii

Sarcinile puse în coadă rămân în memorie până se finalizează, astfel încât fiecare spațiu de lucru și fiecare aplicație pot deține doar o parte din memoria cozii pe care celelalte o lasă liberă. Un singur job este, de asemenea, limitat la 20 MB de date utile serializate.

`enqueueJobs` raportează ce a utilizat fiecare apel. Aceste câmpuri necesită Twenty 2.57.0 sau o versiune ulterioară, care este și versiunea minimă a serverului pentru SDK:

| Câmp              | Ce conține                                                                                                                                                                                |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `locuri de muncă` | `jobId`, `sizeBytes` și [`scheduledAt`](#when-a-job-is-scheduled) ale fiecărei sarcini puse în coadă.                                                                                     |
| `availableBytes`  | Memoria pe care aplicația și spațiul dvs. de lucru o mai pot pune în coadă la momentul acestui apel. `null` când serverul nu limitează memoria cozii. Este o instantanee, nu o rezervare. |

Când se atinge o limită, întregul apel este respins și nu se pune nimic în coadă:

| `subCode` al erorii              | Când                                                       | Detalii                                                |
| -------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------ |
| `JOB_TOO_LARGE`                  | O sarcină depășește limita de dimensiune.                  | `index`, `sizeBytes`, `maxBytes`                       |
| `JOB_QUEUE_MEMORY_LIMIT_REACHED` | Lotul nu încape în cota dvs. Încercați din nou mai târziu. | `requestedBytes`, `availableBytes`, `refusedGroupKeys` |

Păstrați încărcăturile utile mici: transmiteți ID-urile înregistrărilor și preluați înregistrările în timpul rulării, în loc să le încorporați. Dacă `availableBytes` devine insuficient, puneți mai puține sarcini în coadă simultan sau înlănțuiți-le cu `delayMs`.

## Reîncercați după un eșec temporar

Twenty nu reîncearcă fiecare excepție din codul aplicației. O eroare obișnuită lansată este tratată ca un eșec permanent. Pentru un eșec temporar, o funcție logică pusă în coadă poate solicita până la trei reîncercări prin lansarea `RetryableLogicFunctionError`.

```ts
import {
  type LogicFunctionExecutionContext,
  RetryableLogicFunctionError,
} from 'twenty-sdk/logic-function';

export const handler = async (
  _payload: unknown,
  { retryCount, maxRetries }: LogicFunctionExecutionContext,
) => {
  const response = await fetch('https://api.example.com/contacts');

  if (response.status === 429 || response.status >= 500) {
    throw new RetryableLogicFunctionError(
      `The contacts API is temporarily unavailable (${response.status}); retry ${retryCount} of ${maxRetries}`,
    );
  }
};
```

Lansați direct `RetryableLogicFunctionError` atunci când este posibil. Dacă o extindeți, nu îi înlocuiți `name`: Twenty recunoaște numele serializat `RetryableLogicFunctionError` în toate mediile de execuție.

`retryCount` este `0` pentru execuția inițială și crește doar atunci când codul aplicației solicită o reîncercare. `maxRetries` este cel mult `3` și poate fi mai mic atunci când sarcina din coadă are o limită totală de reîncercări mai mică. Eșecurile platformei nu cresc `retryCount`, deși consumă în continuare bugetul general de siguranță al cozii.

Coada întârzie încercările de reîncercare folosind backoff exponențial și jitter. Întârzierea exactă nu este garantată în mod intenționat, astfel că codul aplicației nu ar trebui să depindă de producerea unei reîncercări la un moment precis. După ce se atinge `maxRetries`, o altă `RetryableLogicFunctionError` este înregistrată ca eșecul final al aplicației, fără o altă execuție.

<Warning>
Reîncercările rulează din nou întregul handler și se pot produce după ce unele efecte secundare au reușit. Faceți handlerul idempotent înainte de a solicita reîncercări.
</Warning>

## Reacționează când un job eșuează definitiv

O execuție pusă în coadă se poate încheia fără ca codul tău să ajungă la propria gestionare a erorilor, de exemplu când atinge `timeoutSeconds`. Adaugă `onJobFailure` lângă `handler`, iar Twenty îl apelează o dată când o execuție pusă în coadă a funcției eșuează și nu va fi reîncercată.

```ts src/logic-functions/answer-request.ts
import { defineLogicFunction } from 'twenty-sdk/define';
import { type LogicFunctionJobFailure } from 'twenty-sdk/logic-function';

type AnswerRequestPayload = { requestId: string };

export default defineLogicFunction({
  universalIdentifier: 'b4d7e0f1-5c2a-4e8b-9a3d-6f1e2c7b8a90',
  name: 'answer-request',
  timeoutSeconds: 240,
  handler: async (payload: AnswerRequestPayload) => {
    // ...
  },
  onJobFailure: async ({
    payload,
    error,
  }: LogicFunctionJobFailure<AnswerRequestPayload>) => {
    await markRequestFailed(payload.requestId, error.message);
  },
});
```

`onJobFailure` primește eșecul ca prim argument și același context de execuție ca `handler` drept al doilea:

| Câmp               | Descriere                                                                                                                                                            |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `payload`          | Încărcătura utilă a execuției eșuate.                                                                                                                                |
| `error.type`       | `TimeoutError` pentru un timeout, `name` al erorii pentru o eroare generată sau o eroare de platformă, `UnrecoverableError` când jobul s-a blocat de prea multe ori. |
| `error.message`    | Mesajul de eroare.                                                                                                                                                   |
| `job.id`           | Jobul pus în coadă care a eșuat. Pentru un job pe care l-ai pus în coadă cu `enqueueJobs`, `jobId` pe care l-a returnat.                                             |
| `job.attemptsMade` | Câte încercări în coadă a făcut jobul înainte de a eșua definitiv.                                                                                                   |

Rulează ca propriul job pus în coadă, într-un proces nou, cu `timeoutSeconds` al funcției. ID-ul jobului este ID-ul jobului eșuat urmat de `.on-failure`, astfel încât îl poți interoga cu `getJobs`, iar un eșec nu îl pornește niciodată de două ori.

Rulează după:

* o eroare generată de codul tău care nu este reîncercată, inclusiv un `RetryableLogicFunctionError` după ce se atinge `maxRetries`;
* un timeout;
* o eroare de platformă după ce jobul pus în coadă nu mai are încercări disponibile;
* blocarea de două ori a procesului worker care rulează jobul. Coada rulează din nou jobul după prima blocare, iar după a doua marchează jobul ca eșuat cu `job stalled more than allowable limit`. Apoi `onJobFailure` rulează când un worker preia jobul, astfel că, după o întrerupere completă, rulează când workerii revin.

Nu rulează:

* pentru execuții care nu trec prin coada de joburi, cum ar fi apelurile de instrumente, pașii fluxului de lucru și resolverul unei rute de server (o funcție țintă pe care resolverul o pune în coadă este acoperită);
* când `onJobFailure` însuși eșuează, astfel încât nu poate intra într-o buclă.

<Warning>
Execuția eșuată ar putea să fi finalizat unele efecte secundare înainte de a se opri. Nu rula din nou orbește aceeași activitate din `onJobFailure`; în schimb, înregistrează eșecul sau informează utilizatorul. Fă-l idempotent, deoarece coada îl reîncearcă de până la trei ori în cazul unei erori de platformă. Livrarea se face cu efort maxim: dacă un worker se oprește în momentul dintre eșecul unui job și punerea în coadă a `onJobFailure`, acesta nu rulează.
</Warning>

## Folosește-l: parcurge pe pagini o sincronizare lungă

Forma clasică este o funcție care pune în coadă *ea însăși* cu următorul cursor. Fiecare rulare procesează o pagină de lucru bine în interiorul propriului timeout, iar lanțul se oprește când nu mai rămâne nimic.

```ts src/logic-functions/sync-contacts-page.ts
import { defineLogicFunction } from 'twenty-sdk/define';
import { enqueueJobs } from 'twenty-sdk/logic-function';

const SYNC_CONTACTS_PAGE = '9f1c3d7e-51b8-4a29-8f0d-7c4e2a6b1d33';

const handler = async (params: { cursor?: string }) => {
  const { contacts, nextCursor } = await fetchContactsPage(params.cursor);

  await importContacts(contacts);

  if (nextCursor) {
    await enqueueJobs({
      logicFunctionUniversalIdentifier: SYNC_CONTACTS_PAGE,
      jobs: [{ payload: { cursor: nextCursor } }],
      delayMs: 2_000,
    });
  }

  return { imported: contacts.length, done: !nextCursor };
};

export default defineLogicFunction({
  universalIdentifier: SYNC_CONTACTS_PAGE,
  name: 'sync-contacts-page',
  timeoutSeconds: 120,
  handler,
});
```

## Dispersare pe înregistrare

Când munca este în mod natural pe element, pune în coadă un job per element într-un singur apel și lasă workerii să le proceseze în paralel în loc să iterezi inline.

```ts
const companies = await listCompaniesToEnrich();

await enqueueJobs({
  logicFunctionUniversalIdentifier: ENRICH_COMPANY,
  jobs: companies.map((company) => ({ payload: { companyId: company.id } })),
  retryLimit: 2,
});
```

## Bune practici pentru muncă de lungă durată

Două reguli acoperă aproape orice job lung: folosește recursie în locul buclelor și procesează un segment limitat per rulare.

O rulare care încearcă să facă totul este modul de eșec — atinge timeout-ul, iar la o reîncercare începe din nou totul de la zero. În schimb, dimensionează un segment astfel încât să se termine confortabil în interiorul `timeoutSeconds`, persistă-ți poziția și pune în coadă următoarea rulare.

```ts src/logic-functions/enrich-companies-batch.ts
import { defineLogicFunction } from 'twenty-sdk/define';
import { enqueueJobs, kv } from 'twenty-sdk/logic-function';

const ENRICH_COMPANIES_BATCH = '3f9d1c02-8a44-4f0e-b1d7-9c2e5a7b4f10';
const CHUNK_SIZE = 50;

const handler = async (params: { offset?: number }) => {
  const offset = params.offset ?? 0;
  const companies = await listCompaniesToEnrich({
    offset,
    limit: CHUNK_SIZE,
  });

  for (const company of companies) {
    await enrichCompany(company);
  }

  await kv.set('enrich:progress', { offset: offset + companies.length });

  if (companies.length === CHUNK_SIZE) {
    await enqueueJobs({
      logicFunctionUniversalIdentifier: ENRICH_COMPANIES_BATCH,
      jobs: [{ payload: { offset: offset + CHUNK_SIZE } }],
    });
  }

  return { processed: companies.length, done: companies.length < CHUNK_SIZE };
};

export default defineLogicFunction({
  universalIdentifier: ENRICH_COMPANIES_BATCH,
  name: 'enrich-companies-batch',
  timeoutSeconds: 300,
  handler,
});
```

Ce îl face robust:

* **Dimensionează segmentul pornind de la cel mai lent element, nu de la medie.** `CHUNK_SIZE × worst-case item time` trebuie să încapă în `timeoutSeconds` cu marjă, altfel „coada” unui segment se pierde când rularea este întreruptă.
* **Fă condiția de terminare explicită.** Apelează recursiv doar cât timp a revenit un segment complet. Un lanț care se oprește doar pe baza „niciun rezultat” va continua la nesfârșit dacă sursa returnează vreodată o pagină scurtă la mijloc.
* **Păstrează progresul înainte de a pune în coadă următoarea rulare**, astfel încât o verigă eșuată să repornească de la ultimul segment finalizat în loc de la început.
* **Păstrează fiecare segment idempotent.** Reprocesarea unui segment după o reîncercare nu trebuie să ducă la scrieri duble — leagă scrierile de înregistrarea sau ID-ul extern pe care îl procesezi.
* **Ritmați un fan-out care accesează o terță parte cu limită de rată** cu un [`limiter`](#pace-runs-with-a-limiter) sau utilizați un lanț împărțit în bucăți cu `delayMs`. Mii de sarcini puse în coadă fără niciuna dintre acestea devin toate eligibile imediat.
