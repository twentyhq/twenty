An app is written once and runs once per workspace that installs it. Every trigger and every API call is multiplied by the number of installs, and most of what those installs call is shared: the application API budget, the job queue, and any provider key stored as a server variable. The [public apps](https://github.com/twentyhq/twenty/tree/main/packages/twenty-apps/public) learned the lessons below the hard way.

## Crons fire in every workspace at the same minute

Once a minute the server walks every active workspace and enqueues one run for every logic function whose pattern matches. The same pattern means the same minute everywhere, and the runs then hit the same budgets.

```text
   pattern "0 3 * * *"                  the server, every minute
                                                  │
              ┌───────────────┬───────────────────┼───────────────┐
              ▼               ▼                   ▼               ▼
        workspace A     workspace B     workspace C   ...   workspace N
          03:00:00        03:00:00        03:00:00            03:00:00
              │               │                   │               │
              └───────────────┴─────────┬─────────┴───────────────┘
                                        ▼
                     one app API budget, one provider API key
                         N bursts in the same second  →  429
```

The Call Recorder, installed on 700+ workspaces, triggered provider rate-limit alerts with two crons running every 15 minutes. What worked:

- Keep the fast path on database events, webhooks and user actions. A cron is a backstop for what those missed.
- Run it daily, off-peak, at a minute your other crons do not use.
- Make the cron handler only enqueue the real work, with a stable per-workspace delay so N runs spread over a window instead of bursting:

```ts
const delayMs =
  createHash('sha256').update(workspaceId).digest().readUInt32BE(0) %
  (60 * 60 * 1000);
```

- Bound what one run touches: a time window, one page per job, an early exit when there is nothing to do.
- A changed pattern reaches an install only on upgrade, so bump the app version when you change one.

## Learnings

1. **Narrow and batch database event triggers.** A mailbox sync emits one event per message, and one run per event overflowed the workers. Declare `updatedFields` so the server filters before a run exists, set `batchMode: true`, and fold the batch into distinct records before the first API call. The Last Contact app listens to `messageParticipant.updated` on `personId` rather than `message.created`: that is the transition it cares about, and it fires once per link. See [Batching database events](/developers/extend/apps/logic/logic-functions#batching-database-events).

2. **Detect, then backfill with one delayed job.** When an event reveals more work than it carries, do not do it inline and do not enqueue it once per event. Mark what needs work, then enqueue one job with a `delayMs` and a deterministic `jobId` that includes a time window. The queue ignores an id it already holds, so a burst collapses into a single run that starts once the burst has settled. See [Choose your own job id](/developers/extend/apps/logic/background-jobs#choose-your-own-job-id).

3. **Do not trigger yourself.** An app that writes to the object it listens to re-fires on its own writes. Exclude the fields you write from `updatedFields`, recognize your own writes with data you own rather than `updatedBy`, and set `isAuditLogged: false` on fields you rewrite on every sync so they stay off the record timeline.

4. **Pace fan-outs with `delayMs`.** A thousand jobs enqueued at once all become eligible at once. Group the work into slots sized from the shared budget, delay slot `i` by `i` minutes, and delay the next page by the slots the current page used. `retryLimit` bounds one job, not a re-enqueue chain, so carry the attempt count in the payload. Only `RetryableLogicFunctionError` is redelivered. On a `429`, re-enqueue with the `Retry-After` delay instead of sleeping through it. See [Background jobs](/developers/extend/apps/logic/background-jobs).

5. **Count your Twenty API calls per run.** The application budget is 500 calls per minute, shared by every workspace on the instance, and consumed per root field: a `createMany` with `upsert: true` carrying 200 records is one call. Read with `in` filters over the batch and write once per object. The Last Contact app went from 435 to 585 calls per batch down to 9. Retry `429`, `502`, `503` and `504` yourself with backoff, jitter and a cap on attempts.

6. **Cache what does not change.** The Slack app asked Slack for its bot user id on every channel-join event. It now writes the id to the [key-value store](/developers/extend/apps/logic/key-value-store) when the connection is registered; reconnecting re-runs the hook, so the cache corrects itself without a TTL.

7. **Provider budgets are shared too.** A server variable API key is one provider account for every workspace. Bound the provider client to your run with a request timeout and a small retry budget, since library defaults retry for minutes. List once per run and match in memory instead of one lookup per record. Store the idempotency key and an "attempted at" marker on the record before calling the provider, and respect the provider's idempotency window: trusting a key for 12 hours when the provider forgot it after one created twin bots that were both billed.

8. **Make every run idempotent and resumable.** Derive record ids from the provider's ids so webhooks, syncs and backfills converge on one row. Keep a status field with terminal states. Write with a filter that encodes what you expect and treat zero matched rows as "someone else got there first". Persist the cursor before enqueuing the next page. Charge credits only from the write that won, and never rethrow after a paid step succeeded.

9. **Ack webhooks fast and dedupe them.** The server route resolver verifies the signature and dispatches; the queued target does the work. A late ack means a redelivery, and each one is a billed invocation, so forward the provider's retry headers and log them. Dedupe with a unique index on the provider's message key or a deterministic job id.

10. **Backfill on purpose.** Run it on a fresh install, on an upgrade that requires it (compare `previousVersion` and `newVersion`), or on an explicit user action with a visible count. Never unattended when it bills. Bound the window and the pages, skip what is already there, and expose the batch size as a server variable. Post-install hooks run one at a time on their own queue, so a backfill whose jobs would compete for the same API budget can simply run sequentially inside the hook.

11. **Check credits before you spend and ship a health check.** `getCreditAvailability()` fails open, so a hiccup never cancels work; the Call Recorder checks it ten minutes before a bot joins. `defineHealthCheck` turns an empty column into "no synced inbox yet" with a button to the fix. See [Checking before you spend](/developers/extend/apps/logic/credits#checking-before-you-spend) and [Health check](/developers/extend/apps/logic/logic-functions#health-check).
