`defineWorkflow` from `twenty-sdk/define` declares a workflow in the application's manifest. The POC supports manual triggers and every existing workflow action type. Declare referenced functions and agents in the same app. Functions used by `LOGIC_FUNCTION` steps must expose `workflowActionTriggerSettings`. `CODE` steps follow the platform rule for running a function on demand: the function must expose `workflowActionTriggerSettings` unless the installing workspace owns the app's registration.

```ts src/workflows/greeting.workflow.ts
import { defineWorkflow } from 'twenty-sdk/define';
import { GREET_UNIVERSAL_IDENTIFIER } from '../logic-functions/greet.function';

const GREET_STEP_ID = 'a90528b8-5a87-4cd8-8dc5-b93f7e864c15';

export default defineWorkflow({
  universalIdentifier: '96cfb613-dc0f-47c4-9410-8971ebc3c263',
  name: 'Application greeting',
  version: {
    universalIdentifier: '0f1d0260-e781-4501-9d26-1e7f73585331',
    trigger: {
      universalIdentifier: '02720fe3-1977-4306-a9c3-66f7c99e3199',
      type: 'MANUAL',
      nextStepIds: [GREET_STEP_ID],
    },
    steps: [
      {
        universalIdentifier: GREET_STEP_ID,
        name: 'Greet',
        type: 'LOGIC_FUNCTION',
        logicFunctionUniversalIdentifier: GREET_UNIVERSAL_IDENTIFIER,
        input: { greeting: 'Before upgrade' },
        nextStepIds: [],
      },
    ],
  },
});
```

The imported `GREET_UNIVERSAL_IDENTIFIER` is the universal identifier of the app's greeting logic function. That function accepts `{ greeting: string }` and returns the greeting.

| Field                                      | Meaning                                                       |
| ------------------------------------------ | ------------------------------------------------------------- |
| `universalIdentifier`, `name`              | Stable workflow UUID and display name                         |
| `version.universalIdentifier`              | Stable UUID for the workflow's single version                 |
| `version.trigger`                          | Universal identifier, `type: 'MANUAL'`, and starting step IDs |
| `version.steps`                            | Nonempty list of workflow steps                               |
| Step `universalIdentifier`, `name`, `type` | Stable step UUID, display name, and action type               |
| Step `logicFunctionUniversalIdentifier`    | App function UUID for `CODE` or `LOGIC_FUNCTION` steps        |
| Step `input`                               | Typed action input; function arguments for function steps     |
| `nextStepIds`                              | Step universal identifiers; use `[]` for a terminal step      |

Workflow, version, trigger and step UUIDs must be distinct. Cycles are allowed only when a loop body returns to its enclosing iterator; all destinations must exist, and every step must be reachable from the trigger. Runtime function IDs are resolved for the installing workspace, including functions created in the same synchronization.

## Supported steps

`defineWorkflow` supports every existing workflow action: `CODE`, `LOGIC_FUNCTION`, `SEND_EMAIL`, `DRAFT_EMAIL`, `CREATE_CALENDAR_EVENT`, `CREATE_RECORD`, `UPDATE_RECORD`, `DELETE_RECORD`, `UPSERT_RECORD`, `FIND_RECORDS`, `PICK_RECORD`, `FORM`, `HTTP_REQUEST`, `AI_AGENT`, `CLASSIFY`, `FILTER`, `IF_ELSE`, `ITERATOR`, `DELAY`, and `EMPTY`.

Every step has a stable `universalIdentifier`, `name`, `type`, `input`, and `nextStepIds`. Optional `position`, `outputSchema`, `expectedOutputSchema`, and `errorHandlingOptions` use the existing workflow action formats. Inputs use the native action schemas with these portable metadata references:

| Step                         | Manifest reference                                                  | Resolved at installation                                                                       |
| ---------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `CODE`, `LOGIC_FUNCTION`     | Top-level `logicFunctionUniversalIdentifier`                        | An app-declared function ID; `LOGIC_FUNCTION` additionally requires an exposed workflow action |
| Record actions               | `input.objectUniversalIdentifier`                                   | Object API name                                                                                |
| `FIND_RECORDS` filters/sorts | `fieldMetadataUniversalIdentifier`                                  | Field ID, checked against the selected object                                                  |
| `PICK_RECORD` load balancing | `loadBalance.objectUniversalIdentifier`, `fieldUniversalIdentifier` | Object and field API names                                                                     |
| `FILTER`, `IF_ELSE` filters  | Optional `fieldMetadataUniversalIdentifier`                         | Field ID                                                                                       |
| `FORM` record picker         | `settings.objectUniversalIdentifier`                                | Object API name                                                                                |
| `AI_AGENT`                   | Optional `input.agentUniversalIdentifier`                           | An app-declared agent ID                                                                       |

Objects and fields can come from the same installation or metadata already installed in the workspace. Record values and `fieldsToUpdate` use API field names. Record IDs and connected-account IDs are runtime data, not metadata universal identifiers; provide workspace-specific values or workflow variable references. Steps run with the application's permissions, described below.

A record step can use an object declared by the same app:

```ts
{
  universalIdentifier: CREATE_COMPANY_STEP_ID,
  name: 'Create company',
  type: 'CREATE_RECORD',
  input: {
    objectUniversalIdentifier: COMPANY_UNIVERSAL_IDENTIFIER,
    objectRecord: { name: '{{trigger.companyName}}' },
  },
  nextStepIds: [],
}
```

For `IF_ELSE`, each branch's `nextStepIds` identifies its entry steps. For `ITERATOR`, `input.initialLoopStepIds` identifies the loop body, while the iterator's `nextStepIds` identifies the steps after the loop. Every loop-body path must return to its enclosing iterator through `nextStepIds`. The iterator advances on that return edge. Its own `nextStepIds` runs after the loop completes. Manifest validation checks these edges for missing steps, invalid cycles, missing iterator returns, unknown variable sources and reachability.

`CODE` uses a separately declared app logic function rather than inline source. External integrations still require their normal setup: connected accounts for email/calendar, AI availability for agent/classification actions, and reachable HTTP endpoints. Supporting their definitions does not bypass those requirements or change their permissions.

## Permissions

Starting an app workflow and running its steps are authorized separately. Starting it keeps the usual checks: the member needs the Workflows permission and must be able to see the workflow. A token issued to an application can start that application's workflows and workspace workflows, but not another application's workflows.

Each step then runs with the application's default role, never with more than the member who started the run. The effective permissions are the intersection of the member's role and the app role, so object, field and row-level permissions of both apply. An app without a default role cannot run steps.

| Step | Runs with |
| --- | --- |
| Record actions | The intersection of the member's role and the app role |
| `CODE`, `LOGIC_FUNCTION` | The app's own function only. It receives the app token and a token acting for the member within the app role |
| `AI_AGENT` | The app's own agent only. The agent's role is limited by the run's roles, and the code interpreter and campaign drafting tools are unavailable |
| `SEND_EMAIL`, `DRAFT_EMAIL` | Requires `SEND_EMAIL_TOOL` on the app role and the member's role |
| `CREATE_CALENDAR_EVENT` | Requires `CREATE_CALENDAR_EVENT_TOOL` on the app role and the member's role |

Email and calendar steps, including agent tools, only use a connected account owned by the member who started the run or shared with the workspace. Another member's private account is refused, whether it is given as an account ID, a workspace member or picked by default.

Permissions are checked again at every step, including after a delay, a retry or an iterator pass. Nothing about the identity is stored in queued jobs: removing a permission from the app or the member, removing the member, or uninstalling the app makes the next step fail with an error on that step. Only the member who started a run can fill its form, submit it or retry the run.

Workspace workflows keep their current behavior.

## Updates and runs

Synchronization creates one ACTIVE version. Changing the source updates that same version without allocating another workflow or version ID. Keep both universal identifiers stable across releases.

Existing runs retain the graph saved when they started, including their step inputs and edges. Function implementations are not pinned: a step executed after an upgrade uses the current function implementation. Keep functions needed by existing runs available.

Installed app workflows are read-only in the normal workflow editor and APIs. Open the workflow show page and click Run to start a run. Change the app source and sync to update the definition.

## POC boundaries

Removing a workflow from a full manifest sync, replacing its version universal identifier, and adopting a workspace-owned workflow are rejected. Additive pre-install synchronization can omit existing workflows.

Automated triggers, command-menu registration, duplication, export/pull, uninstall safety, execution-dependency pinning and production rollback support remain separate work. Existing workspace-owned workflow APIs and rollback mirrors retain their current lifecycle.


Application workflows are experimental. Enable `IS_APPLICATION_WORKFLOWS_ENABLED` to install or update workflow definitions and start new runs, and enable `IS_WORKFLOW_CORE_INDEX_PAGE_ENABLED` for the core workflow UI. Both flags default off unless configured. Disabling the application-workflow flag blocks installation/updates containing workflows and hides Run; it does not delete definitions or interrupt already-started runs. The older workspace UI cannot display these core-only definitions. Uninstall safety and dependency pinning remain outside this POC.

Output schemas are populated during installation without executing steps. Explicit step `outputSchema` takes precedence. CODE and LOGIC_FUNCTION steps can reuse the referenced function's `workflowActionTriggerSettings.outputSchema`; otherwise provide an `expectedOutputSchema` containing a representative result. HTTP_REQUEST also uses `expectedOutputSchema`. AI_AGENT uses the referenced agent's response format. Arbitrary code and HTTP response shapes cannot be inferred without an output declaration. Keep declarations in sync with the implementation.

Record-write field names are checked against metadata from the target workspace and the same app installation. UPDATE_RECORD must select existing fields and provide their values in `objectRecord`.

Record, find-records and form output schemas are computed from metadata by the existing workflow editor; core iterator schemas are fetched from the schema API. These dynamic schemas are not materialized by this installer. Installation validates variable source steps and validates property paths when a declared schema is available. Record sorts must use `recordSorts` with field universal identifiers; raw `gqlOperationOrderBy` is not accepted in application manifests.
