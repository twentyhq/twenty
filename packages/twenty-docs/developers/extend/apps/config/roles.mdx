## Overview

A **role** is a permission set: which objects an app can read or write, which fields it can see, and which platform-level capabilities it can use. Every app's logic functions and front components inherit the permissions of the role marked with `defineApplicationRole()` (see [The default function role](#the-default-function-role) below).

```ts src/roles/restricted-company-role.ts
import {
  defineRole,
  STANDARD_OBJECT_UNIVERSAL_IDENTIFIERS,
  SystemPermissionFlag,
} from 'twenty-sdk/define';

export default defineRole({
  universalIdentifier: '2c80f640-2083-4803-bb49-003e38279de6',
  label: 'My new role',
  description: 'A role that can be used in your workspace',
  canUpdateAllSettings: false,
  canAccessAllAgentChatChannels: false,
  canBeAssignedToAgents: false,
  canBeAssignedToUsers: false,
  canBeAssignedToApiKeys: false,
  recordsPermissions: {
    canReadAllRecords: false,
    canUpdateAllRecords: false,
    canSoftDeleteAllRecords: false,
    canDestroyAllRecords: false,
    objects: [
      {
        objectUniversalIdentifier:
          STANDARD_OBJECT_UNIVERSAL_IDENTIFIERS.company.universalIdentifier,
        canReadAllRecords: true,
        canUpdateAllRecords: true,
        canSoftDeleteAllRecords: false,
        canDestroyAllRecords: false,
        unreadableFields: [
          STANDARD_OBJECT_UNIVERSAL_IDENTIFIERS.company.fields.name
            .universalIdentifier,
        ],
      },
    ],
  },
  permissionFlagUniversalIdentifiers: [SystemPermissionFlag.WORKSPACE_APPS],
});
```

`recordsPermissions` holds everything a role can do on records:

- `canReadAllRecords`, `canCreateAllRecords`, `canUpdateAllRecords`, `canSoftDeleteAllRecords` and
  `canDestroyAllRecords` at its top level apply to **every object**. `canCreateAllRecords` follows
  `canUpdateAllRecords` when it is not set.
- `objects` lists what differs for one object: the same five grants for all its records,
  `unreadableFields` and `uneditableFields` (field universal identifiers; a field that cannot be
  read cannot be edited either), and its [row-level records permissions](#row-level-security).

<Note>
  `SystemPermissionFlag.USER_APPS` and `SystemPermissionFlag.WORKSPACE_APPS`
  are available from `twenty-sdk` 2.54 onward; earlier versions name them
  `CONNECTED_ACCOUNTS` and `APPLICATIONS`. The old names are deprecated aliases
  for the same flags, and a role keeps each flag once. Enumerating
  `SystemPermissionFlag`, for example with `Object.keys`, still lists the old
  names. The API also reports these flags under their old keys, for example in
  `currentUserWorkspace.permissionFlags`.
</Note>

## Row-level security

Row-level permissions require the **Organization plan or above** — see
[pricing](https://twenty.com/pricing). What happens on a plan without the entitlement is covered in
the notes at the end of this section.

Object and field permissions decide _which objects and fields_ a role can touch. **Row-level
permission predicates** go further and decide _which records_ a role can see and act on — for
example, a self-service role where each external user sees only their own records.

An object of `recordsPermissions.objects` can restrict some operations to part of its records with
`rowLevelRecordsPermissions`, a list of rules. A rule grants operations (`canReadRecords`,
`canCreateRecords`, `canUpdateRecords`, `canSoftDeleteRecords`, `canDestroyRecords`) on the records
matched by the predicates nested inside it. A rule can also carry its own `unreadableFields` and
`uneditableFields`, which apply to the records it matches; such a rule needs at least one predicate
group.

A predicate references a field by its `universalIdentifier`, an `operand`, and (optionally) a
workspaceMember field whose value is injected at query time — so you can express "the record's owner
relation **is** the current workspace member". This role can create any company, but reads and
updates only the companies it owns:

```ts src/roles/partner-role.ts
import {
  defineRole,
  RowLevelPermissionPredicateOperand,
  STANDARD_OBJECT_UNIVERSAL_IDENTIFIERS,
} from 'twenty-sdk/define';

import { ACCOUNT_OWNER_FIELD_UNIVERSAL_IDENTIFIER } from '../fields/account-owner.field';

export default defineRole({
  universalIdentifier: 'c3c1dc2e-1a08-4de5-abb7-2139b3d99343',
  label: 'Partner',
  description: 'External partner — sees only its own records',
  canBeAssignedToUsers: true,
  recordsPermissions: {
    objects: [
      {
        objectUniversalIdentifier:
          STANDARD_OBJECT_UNIVERSAL_IDENTIFIERS.company.universalIdentifier,
        canCreateAllRecords: true,
        rowLevelRecordsPermissions: [
          {
            universalIdentifier: 'a9e8d7c6-5b4a-4c3d-9e2f-000000000000',
            canReadRecords: true,
            canUpdateRecords: true,
            predicates: [
              {
                universalIdentifier: 'd0f0c1a2-3b4c-4d5e-8f60-111111111111',
                fieldUniversalIdentifier: ACCOUNT_OWNER_FIELD_UNIVERSAL_IDENTIFIER,
                operand: RowLevelPermissionPredicateOperand.IS,
                workspaceMemberFieldUniversalIdentifier:
                  STANDARD_OBJECT_UNIVERSAL_IDENTIFIERS.workspaceMember.fields.id
                    .universalIdentifier,
              },
            ],
          },
        ],
      },
    ],
  },
});
```

Because these permissions ship in the manifest, they are created, updated, and removed together with
the role on every install and upgrade — there is no separate post-install step to keep in sync.

<Warning>
  An operation granted on **all records** wins over the rules. Do not grant with `can…AllRecords`,
  on the object or for every object, the operations a rule is meant to restrict: when the role
  grants one for every object, set the object's `can…AllRecords` to `false`. `defineRole` warns
  when a rule is shadowed this way.
</Warning>

An object can declare several rules. A record is reachable for an operation as soon as one rule
granting that operation matches it, so one rule can let a partner read the accounts of its region
while another lets it update only the accounts it owns.

### Combining predicates with groups

The predicates of a rule are combined with `AND`. To combine some of them with `OR` (or to nest
logic), add `predicateGroups` to the rule: a group has a `logicalOperator`, its own `predicates`,
and may contain further `predicateGroups`. This role lets a partner see an Opportunity it either
**owns** or is the **point of contact** for:

```ts src/roles/partner-opportunities-role.ts
import {
  defineRole,
  RowLevelPermissionPredicateGroupLogicalOperator,
  RowLevelPermissionPredicateOperand,
  STANDARD_OBJECT_UNIVERSAL_IDENTIFIERS,
} from 'twenty-sdk/define';

const OPPORTUNITY = STANDARD_OBJECT_UNIVERSAL_IDENTIFIERS.opportunity;
const CURRENT_MEMBER =
  STANDARD_OBJECT_UNIVERSAL_IDENTIFIERS.workspaceMember.fields.id
    .universalIdentifier;

export default defineRole({
  universalIdentifier: 'b2a1c0d9-8e7f-4a6b-9c5d-222222222222',
  label: 'Partner (opportunities)',
  canBeAssignedToUsers: true,
  recordsPermissions: {
    objects: [
      {
        objectUniversalIdentifier: OPPORTUNITY.universalIdentifier,
        rowLevelRecordsPermissions: [
          {
            universalIdentifier: 'f6e5d4c3-2a1b-4e0d-8a9f-666666666666',
            canReadRecords: true,
            predicateGroups: [
              {
                universalIdentifier: 'c3b2a1d0-9f8e-4b7a-8d6c-333333333333',
                logicalOperator:
                  RowLevelPermissionPredicateGroupLogicalOperator.OR,
                predicates: [
                  {
                    universalIdentifier: 'd4c3b2a1-0e9f-4c8b-9e7d-444444444444',
                    fieldUniversalIdentifier:
                      OPPORTUNITY.fields.owner.universalIdentifier,
                    operand: RowLevelPermissionPredicateOperand.IS,
                    workspaceMemberFieldUniversalIdentifier: CURRENT_MEMBER,
                  },
                  {
                    universalIdentifier: 'e5d4c3b2-1f0e-4d9c-8f8e-555555555555',
                    fieldUniversalIdentifier:
                      OPPORTUNITY.fields.pointOfContact.universalIdentifier,
                    operand: RowLevelPermissionPredicateOperand.IS,
                    workspaceMemberFieldUniversalIdentifier: CURRENT_MEMBER,
                  },
                ],
              },
            ],
          },
        ],
      },
    ],
  },
});
```

<Note>
  Servers older than Twenty 2.59 do not read `recordsPermissions`: declare `engines.twenty` as
  `>=2.59.0` in `package.json` when your app must not install on them.
</Note>

### Deprecated properties

Before `recordsPermissions`, a role declared the same permissions with separate properties. They
still work, `defineRole` prints a deprecation warning naming the ones a role uses, and the build
converts them, so the manifest sent to Twenty only contains `recordsPermissions`:

| Deprecated | Write instead |
|---|---|
| `canReadAllObjectRecords`, `canUpdateAllObjectRecords`, `canSoftDeleteAllObjectRecords`, `canDestroyAllObjectRecords` | `recordsPermissions.canReadAllRecords` and the other `can…AllRecords` |
| `objectPermissions` with `canReadObjectRecords`, … | an entry of `recordsPermissions.objects` with `canReadAllRecords`, … |
| `fieldPermissions` with `canReadFieldValue: false` / `canUpdateFieldValue: false` | `unreadableFields` / `uneditableFields` on the object |
| `rowLevelPermissionPredicates`, `rowLevelPermissionPredicateGroups` | `rowLevelRecordsPermissions` on the object, with the predicates and groups nested in a rule |

Predicates declared on the role had no grants of their own. They are converted to one rule per
top-level predicate group, and one for the ungrouped predicates of each object. The rule takes the
operations the role had on that object, and the object's `can…AllRecords` are set to `false` so
that the predicates keep restricting it.

Notes:

- Give every rule, predicate and group a stable `universalIdentifier` (any uuid) — it keys the entity
  across upgrades.
- Predicates can reference fields owned by your app or by Twenty's standard objects.
- Row-level security is enforced for workspaces on the **Organization plan or above**. On other
  plans the rules declared in an app manifest still sync, they are simply not enforced.
- The Metadata API behaves differently from the manifest here: without the entitlement,
  `upsertRowLevelPermissionPredicates` is rejected with
  `ROW_LEVEL_PERMISSION_FEATURE_DISABLED` rather than syncing. A workspace on a plan that does not
  include row-level security therefore cannot create predicates outside of an app manifest, even
  though the `rowLevelPermissionPredicates` field is present on the `Role` type when you introspect
  the schema.

## The default function role

When you scaffold a new app, the CLI creates a default role file declared with `defineApplicationRole()`:

```ts src/roles/default-role.ts
import { defineApplicationRole } from 'twenty-sdk/define';

export const DEFAULT_ROLE_UNIVERSAL_IDENTIFIER =
  'b648f87b-1d26-4961-b974-0908fd991061';

export default defineApplicationRole({
  universalIdentifier: DEFAULT_ROLE_UNIVERSAL_IDENTIFIER,
  label: 'Default function role',
  description: 'Default role for function Twenty client',
  canUpdateAllSettings: false,
  canBeAssignedToAgents: false,
  canBeAssignedToUsers: false,
  canBeAssignedToApiKeys: false,
  recordsPermissions: {
    canReadAllRecords: true,
    canUpdateAllRecords: false,
    canSoftDeleteAllRecords: false,
    canDestroyAllRecords: false,
  },
  permissionFlagUniversalIdentifiers: [],
});
```

`defineApplicationRole()` is a thin wrapper around `defineRole()` that flags **the** role used as your application's default at install time. Validation is identical to `defineRole`, but the build pipeline auto-wires its `universalIdentifier` into the application manifest's `defaultRoleUniversalIdentifier` — so you do not need to reference it from [`defineApplication`](/developers/extend/apps/config/application) yourself.

Notes:

- Exactly **one** `defineApplicationRole(...)` is allowed per app — the manifest build will fail if it finds more than one.
- Use `defineRole()` (not `defineApplicationRole()`) for any **additional** roles your app ships.
- Setting `defaultRoleUniversalIdentifier` explicitly on `defineApplication()` is still supported for backward compatibility, but is deprecated in favor of `defineApplicationRole()`. It can also name a role your app does not define, such as the workspace custom application's built-in default role kept by `twenty app pull`; the build then cannot check that role, so it must exist in the target workspace.
- A role that workspace members or API keys can be assigned (`canBeAssignedToUsers` or `canBeAssignedToApiKeys`, both `true` when omitted) is a custom role and requires the **Organization plan or above**: on other plans the install is refused. Keep both `false` on roles that only your app and its agents run as.

### Agent roles

The application role is what a workspace reviews when it installs your app, so it must cover everything the app itself can do. Any role you assign to an agent through `roleUniversalIdentifier` on `defineAgent()` must not grant more than the application role: no object action, field access, permission flag or row-level scope the application role lacks. If it does, the build fails with an error listing the excess grants. Roles your app ships for workspace members or API keys are not held to this rule, since the app never runs with them. The check needs the application role in your app's source, so it is skipped when the default role is defined elsewhere.

## Best practices

- Start from the scaffolded role, then progressively restrict it — the default grants broad read access, which is rarely what you want in production.
- List in `recordsPermissions.objects` only the objects your functions actually need, and use `unreadableFields` and `uneditableFields` to hide or lock the fields they do not.
- `permissionFlagUniversalIdentifiers` control access to platform-level capabilities. Keep them minimal.
- A permission flag your app declares with `definePermissionFlag()` carries a `permissionType`: `'tool'` (the default) for a capability an agent or a user can be granted, `'settings'` for a flag that unlocks a settings area.
- See a working example: [`examples/hello-world/src/roles/default-role.ts`](https://github.com/twentyhq/twenty/blob/main/packages/twenty-apps/examples/hello-world/src/roles/default-role.ts).
