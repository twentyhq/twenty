## Обзор

После того как ваше приложение [собрано и протестировано локально](/ru/developers/extend/apps/getting-started/concepts), у вас есть два пути для его распространения:

* **Разверните tar-архив** — загрузите своё приложение напрямую на конкретный сервер Twenty для внутреннего или частного использования.
* **Публикация в npm** — опубликуйте свой пакет, [заявите права на него в Twenty](#claiming-your-app) и завершите его настройку, чтобы другие рабочие пространства могли находить и устанавливать его.

Оба пути начинаются с одного и того же шага **build**.

## Владение регистрацией

Публикация приложения создаёт **регистрацию приложения**: идентификатор приложения в инстансе, общий для всех рабочих пространств, которые его устанавливают. Она содержит запись приложения в маркетплейсе, его клиент OAuth и его серверное состояние — `serverVariables`, настраиваемые оператором, и записи с областью действия `server` в [хранилище ключей и значений](/ru/developers/extend/apps/logic/key-value-store).

`universalIdentifier` уникален во всём инстансе, а регистрация принадлежит не более чем одному рабочему пространству (её владельцу) — либо никому, пока не будет заявлена, — поэтому установка приложения и разработка приложения — это два разных права:

| Действие                                                  | Требование                                                                                                                     |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Установка приложения                                      | Приложение размещено на маркетплейсе, предустановлено оператором или его регистрация принадлежит вашему рабочему пространству. |
| Разработка приложения (`twenty app dev`, `apply`, `plan`) | Регистрация принадлежит вашему рабочему пространству.                                                                          |

Синхронизация кода и манифеста с идентификатором является заявлением об авторстве, поэтому возможность установить приложение никогда не даёт права публиковать код под его идентификатором. Рабочему пространству, не являющемуся владельцем, будет отказано независимо от того, размещено ли приложение, предустановлено или является приватным.

К такому отказу приводят две ситуации:

* **Идентификатор принадлежит другому рабочему пространству.** Измените `universalIdentifier` в конфигурации приложения — это обычное решение, если вы создали форк чужого приложения. Если вам нужно сохранить идентификатор, рабочее пространство-владелец должно передать регистрацию вашему рабочему пространству.
* **Идентификатор не принадлежит ни одному рабочему пространству.** Приложения, импортированные синхронизацией каталога маркетплейса, изначально не имеют владельца. [Заявите права на своё приложение с помощью GitHub](#claiming-your-app), прежде чем разрабатывать его. Публикация с подтверждением происхождения npm предоставляет доказательство авторства; она не назначает автоматически рабочее пространство владельца в Twenty.

## Сборка вашего приложения

Выполните команду сборки, чтобы проверить типы и собрать приложение:

```bash filename="Terminal"
twenty app build
```

Выполняет проверку типов и собирает приложение во временный снимок CLI. Используйте `--json` для проверки манифеста и метаданных артефакта. `twenty app publish` создаёт сам пакет; отдельная сборка tarball-архива не требуется.

## Развертывание на сервер (tarball)

Для приложений, которые вы не хотите делать общедоступными — собственные инструменты, интеграции только для предприятий или экспериментальные сборки — вы можете развернуть tarball напрямую на сервер Twenty.

### Требования

Перед развертыванием вам нужен настроенный remote, указывающий на целевой сервер. Remotes локально хранят URL сервера и учётные данные аутентификации в `~/.twenty/config.json`.

Добавьте remote:

```bash filename="Terminal"
twenty auth login --url https://your-twenty-server.com --name production
```

### Развертывание

Соберите и загрузите ваше приложение на сервер в одном шаге:

```bash filename="Terminal"
twenty app publish --private
# To deploy to a specific remote:
# twenty app publish --private --remote production
```

### Общий доступ к развернутому приложению

Приложения в формате tarball не отображаются в публичном маркетплейсе, поэтому другие рабочие пространства на том же сервере не найдут их при просмотре. Чтобы поделиться развернутым приложением:

1. Перейдите в **Настройки > Разработчики > Приложения** и откройте своё приложение в разделе **Мои приложения**
2. На вкладке **Распространение** нажмите **Копировать ссылку для общего доступа**
3. Поделитесь этой ссылкой с пользователями в других рабочих пространствах — она ведёт их прямо на страницу установки приложения

Ссылка общего доступа использует базовый URL сервера (без какого-либо поддомена рабочего пространства), поэтому она работает для любого рабочего пространства на сервере.

### Управление версиями

При обновлении уже развернутого tarball-приложения сервер требует, чтобы значение `version` в `package.json` было **строго выше** (согласно упорядочиванию по [semver](https://semver.org)), чем текущая развернутая версия. Повторное развертывание той же версии или отправка более ранней версии отклоняется, когда сервер регистрирует загруженный tarball, который затем снова удаляется. Вы увидите ошибку `VERSION_ALREADY_EXISTS` от CLI.

Чтобы выпустить обновление:

1. Увеличьте значение поля `version` в вашем `package.json` (например: `1.2.3` → `1.2.4`, `1.3.0` или `2.0.0`).
2. Выполните `twenty app publish --private` (или `twenty app publish --private --remote production`)
3. Рабочие пространства, в которых приложение установлено и для него включено автообновление (на вкладке «Общие» приложения), обновляются автоматически в фоновом режиме; в остальных рабочих пространствах пользователи увидят доступное обновление в своих настройках

<Note>
  Пререлизные теги работают как ожидается: повышение версии `1.0.0-rc.1` → `1.0.0-rc.2`
  допускается, а финальный релиз вроде `1.0.0` корректно распознаётся как более высокий
  чем `1.0.0-rc.5`. Версия в `package.json` должна сама по себе быть корректной строкой semver
  .
</Note>

### Совместимость версий сервера

Если ваше приложение использует функцию, появившуюся в конкретной версии сервера Twenty (например, провайдеры OAuth, добавленные в v2.3.0), следует объявить минимальную требуемую версию сервера с помощью поля `engines.twenty` в `package.json`:

```json filename="package.json"
{
  "name": "twenty-my-app",
  "version": "1.0.0",
  "engines": {
    "node": "^24.5.0 || ^26.5.1",
    "twenty": ">=2.3.0"
  }
}
```

Значение — это стандартный [диапазон semver](https://github.com/npm/node-semver#ranges). Типовые шаблоны:

| Диапазон                           | Значение                                           |
| ---------------------------------- | -------------------------------------------------- |
| `>=2.3.0`                          | Любой сервер версии 2.3.0 и новее                  |
| `>=2.3.0 \<3.0.0` | 2.3.0 или новее, но ниже следующей мажорной версии |
| `^2.3.0`                           | То же, что и `>=2.3.0 \<3.0.0`    |

**Что происходит при развёртывании и установке:**

* Если `engines.twenty` задано и версия целевого сервера не удовлетворяет диапазону, развёртывание (загрузка tarball-архива) или установка отклоняются с ошибкой `SERVER_VERSION_INCOMPATIBLE` и сообщением, указывающим как требуемый диапазон, так и фактическую версию сервера.
* Если `engines.twenty` **не задано**, проверка версии не выполняется, и приложение принимается на сервере любой версии (обратная совместимость с существующими приложениями). Пустое значение отклоняется как недопустимый диапазон.
* Маркетплейс не отображает приложение, последняя версия которого объявляет диапазон `engines.twenty`, которому сервер не соответствует, или недопустимый диапазон. Приложение остаётся зарегистрированным и видимым в панели администратора.
* Если на сервере `APP_VERSION` не задано, проверка пропускается.

<Note>
  Сервер выполняет окончательную проверку — он проверяет `engines.twenty` как при
  загрузке tarball-архива, так и при установке в рабочем пространстве. Если вы развёртываете tarball вне стандартного процесса или
  устанавливаете из маркетплейса, сервер всё равно принудительно проверяет совместимость.
</Note>

## Автоматизированный CI/CD (рабочие процессы, сгенерированные шаблоном)

Приложения, созданные с помощью `twenty app init`, «из коробки» включают три рабочих процесса GitHub Actions в каталоге `.github/workflows/`. CI запускается без какой-либо настройки, для CD требуется один секрет, а публикация в npm требует однократной настройки доверенного издателя npm (trusted-publisher).

### CI — `ci.yml`

Автоматически запускает интеграционные тесты при каждом пуше в `main` и для каждого pull request.

**Что делает:**

1. Извлекает исходный код вашего приложения.
2. Запускает изолированный тестовый экземпляр Twenty с помощью составного действия `twentyhq/twenty/.github/actions/spawn-twenty-app-dev-test@main`.
3. Включает Corepack и настраивает Node.js на основе вашего `.nvmrc`.
4. Устанавливает закреплённую автономную CLI на этапе **Установка CLI Twenty**.
5. Устанавливает зависимости с помощью `yarn install --immutable`, затем запускает lint, проверку типов и модульные тесты.
6. Запускает `yarn test`, передавая `TWENTY_API_URL` и `TWENTY_API_KEY` из запущенного экземпляра, чтобы ваши тесты могли взаимодействовать с реальным сервером.

**Параметры конфигурации:**

* `TWENTY_VERSION` (переменная окружения, по умолчанию `latest`) — зафиксируйте версию сервера Twenty, используемую в CI, отредактировав это значение в `ci.yml`.
* Параллельные запуски группируются по `github.ref` и отменяют выполняющиеся прогоны при новых пушах.

Секреты не требуются — тестовый экземпляр эфемерен и существует только на время выполнения задания.

### CD — `cd.yml`

Разворачивает ваше приложение на настроенном сервере Twenty при каждом пуше в `main` и, при необходимости, из pull request при наличии метки `deploy`.

**Что делает:**

1. Извлекает head-коммит PR (для PR с меткой) или запушенный коммит.
2. Запускает `twentyhq/twenty/.github/actions/deploy-twenty-app@main` — эквивалент для CI `twenty app publish --private`.
3. Запускает `twentyhq/twenty/.github/actions/install-twenty-app@main`, чтобы новая развернутая версия была установлена в целевое рабочее пространство.

**Обязательная конфигурация:**

| Настройка               | Где                                                                   | Назначение                                                                                                              |
| ----------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `TWENTY_DEPLOY_URL`     | `env` в `cd.yml` (по умолчанию `http://localhost:2020`)               | Сервер Twenty, на который выполняется деплой. Перед первым использованием замените это на URL вашего реального сервера. |
| `TWENTY_DEPLOY_API_KEY` | В репозитории GitHub — **Settings → Secrets and variables → Actions** | Ключ API с правом деплоя на целевом сервере.                                                                            |

<Note>
  Значение `TWENTY_DEPLOY_URL` по умолчанию — `http://localhost:2020` — это заглушка —
  с хостируемого GitHub раннера к ней не будет доступа. Перед включением CD замените его на публичный URL вашего
  сервера (или используйте self-hosted раннер с сетевым доступом).
</Note>

**Запуск предварительного деплоя из PR:**

Добавьте к pull request метку `deploy`. Условие `if:` в `cd.yml` запустит задачу для этого PR, используя его head-коммит, что позволит проверить изменение на целевом сервере до слияния.

### Публикация — `publish.yml`

Публикует ваше приложение в npm с указанием происхождения (provenance), когда вы отправляете тег версии (например, `v1.0.0`), или когда вы запускаете рабочий процесс вручную на вкладке Actions.

**Что делает:**

1. Клонирует ваше приложение, настраивает Node.js и обновляет npm (для доверенной публикации требуется npm версии 11.5.1 или новее).
2. Устанавливает закреплённую автономную CLI на этапе **Установка CLI Twenty**, затем устанавливает зависимости приложения с помощью `yarn install --immutable`.
3. Запускает `twenty app publish`, который собирает и упаковывает изолированный снимок приложения, а затем публикует его в npm. В CI он автоматически добавляет `--provenance` и `--access public`, поэтому в рабочем процессе флаги не требуются.

**Первоначальная настройка:**

На npmjs.com откройте свой пакет > **Settings → Trusted Publisher** и зарегистрируйте этот репозиторий, указав рабочий процесс `publish.yml` (см. [документацию по доверенной публикации в npm](https://docs.npmjs.com/trusted-publishers)). Публикация с подтверждением происхождения удостоверяет, какой репозиторий GitHub собрал пакет. После публикации [заявите права собственности в Twenty](#claiming-your-app).

<Note>
npm принимает подтверждение происхождения только из **публичных** репозиториев с исходным кодом. Если вы публикуете из приватного репозитория, npm отклоняет пакет подтверждения происхождения OIDC с ошибкой `E422 ... Ошибка `Unsupported GitHub Actions source repository visibility: "private"`. Чтобы публиковать из приватного репозитория, отключите подтверждение происхождения, установив `TWENTY_APP_PUBLISH_DISABLE_PROVENANCE: 'true'`в`env`шага публикации (закомментированная подсказка включена в сгенерированный`publish.yml\`):

```yaml filename=".github/workflows/publish.yml"
- name: Publish to npm
  env:
    TWENTY_APP_PUBLISH_DISABLE_PROVENANCE: 'true'
  run: twenty app publish
```

Без подтверждения происхождения GitHub права на пакет нельзя заявить через **Заявить права с помощью GitHub**. Если вам нужен этот процесс назначения владельца, используйте общедоступный репозиторий с подтверждением происхождения.

</Note>

### Закрепление версии CLI

Все три сгенерированных рабочих процесса закрепляют автономную CLI на версии `twenty`, которая запустила `twenty app init`. Этапы **Установка CLI Twenty** в `ci.yml` и `publish.yml` используют `npm install -g twenty@\<version>`. В `cd.yml` и действие развёртывания, и действие установки получают одну и ту же версию через свой входной параметр `cli-version`.

Для обновления одновременно обновите две команды установки и оба входных параметра `cli-version`. Эти закрепления не зависят от версии сервера `TWENTY_VERSION`, используемой в CI, и ссылок на повторно используемые действия ниже.

### Закрепление версий повторно используемых действий

Рабочие процессы `ci.yml` и `cd.yml` ссылаются на повторно используемые действия с указанием `@main`, поэтому обновления действий в репозитории `twentyhq/twenty` подхватываются автоматически. Если вам нужны детерминированные сборки, замените `@main` на SHA коммита или тег релиза в каждой строке `uses:`.

## Публикация в npm

Публикация в npm позволяет разместить ваше приложение на маркетплейсе Twenty. После синхронизации каталога и необходимой [настройки серверных маршрутов](#setting-up-server-routes) рабочие пространства смогут просматривать, устанавливать и обновлять его через интерфейс. Приложения сообщества отображаются, когда пользователи отключают фильтр **Только проверенные**.

### Требования

* Учётная запись [npm](https://www.npmjs.com)
* Ключевое слово `twenty-app` в массиве `keywords` вашего `package.json` (добавьте его вручную — по умолчанию оно не включено в шаблон `twenty app init`)

```json filename="package.json"
{
  "name": "twenty-app-postcard-sender",
  "version": "1.0.0",
  "keywords": ["twenty-app"]
}
```

### Метаданные маркетплейса

Конфигурация `defineApplication()` поддерживает необязательные поля, которые определяют, как ваше приложение отображается в маркетплейсе. Используйте `logo` и `galleryImages`, чтобы ссылаться на изображения из папки `public/`:

```ts src/application-config.ts
export default defineApplication({
  universalIdentifier: '...',
  displayName: 'My App',
  description: 'A great app',
  logo: 'public/logo.png',
  galleryImages: ['public/screenshot-1.png', 'public/screenshot-2.png'],
});
```

См. [аккордеон defineApplication](/ru/developers/extend/apps/config/application#marketplace-metadata) на странице «Создание приложений» для полного списка полей маркетплейса (`author`, `category`, `aboutDescription`, `websiteUrl`, `termsUrl` и т. д.).

#### Рекомендуемые размеры изображений галереи

Маркетплейс отображает `galleryImages` в контейнере с фиксированным соотношением сторон `8:5` (например, `1600×1000 px`).

<Note>
  Изображения галереи с любым соотношением сторон отображаются полностью и никогда не
  обрезаются, но всё, что значительно выше или уже, чем `8:5`, будет иметь
  пустые поля по бокам.
</Note>

#### Ограничение размера изображения

Файл `logo` и каждый файл из `galleryImages` не должны превышать **10 MB**. Более крупные файлы пропускаются при повторном размещении ваших опубликованных ресурсов на маркетплейсе, поэтому они не будут отображаться.

### Публикация

```bash filename="Terminal"
twenty app publish
```

Чтобы опубликовать с определённым dist-tag (например, `beta` или `next`):

```bash filename="Terminal"
twenty app publish --tag beta
```

### Как работает обнаружение приложений в маркетплейсе

Сервер Twenty синхронизирует каталог маркетплейса из реестра npm **каждый час**.

Автономная CLI не имеет команды синхронизации каталога. Дождитесь синхронизации каталога сервером или используйте инструменты администрирования сервера.

Метаданные, отображаемые в маркетплейсе, берутся из вашей конфигурации `defineApplication()` — см. раздел [Метаданные маркетплейса](#marketplace-metadata) выше.

<Note>
Если ваше приложение не определяет `aboutDescription` в `defineApplication()`, маркетплейс автоматически использует `README.md` вашего пакета из npm в качестве содержимого страницы «О приложении». Это означает, что вы можете поддерживать единый README как для npm, так и для маркетплейса Twenty. Если вы хотите другое описание в маркетплейсе, явно задайте `aboutDescription`.

Вкладка About отображает только текст Markdown. Изображения не отображаются, независимо от того, используется ли синтаксис Markdown или теги `<img>`, а необработанный HTML, например бейджи или блоки `\<div align="center">`, отображается как обычный текст.

</Note>

### Публикация через CI

Сгенерированный выше рабочий процесс `publish.yml` автоматически публикует в npm по тегам версий, с provenance. Поскольку `twenty app publish` при запуске в CI добавляет за вас `--provenance` и `--access public`, в рабочем процессе не нужны флаги npm — требуется только однократная настройка доверенного издателя.

Для других систем CI (GitLab CI, CircleCI и т. д.) запустите `yarn install`, затем `twenty app publish`. Provenance создается, когда среда может выпустить токен OIDC, и в противном случае автоматически пропускается.

<Note>
  **npm provenance** добавляет значок доверия к вашему пакету в npm, позволяя пользователям
  проверить, что пакет был собран из конкретного коммита в общедоступном конвейере CI.
  Это также то, что позволяет вам заявить права на ваше приложение в маркетплейсе Twenty.
  Подробности см. в документации по npm provenance
  .
</Note>

После синхронизации пакета с каталогом перейдите к разделу [Заявление прав на приложение](#claiming-your-app). Для заявления прав требуется подтверждение происхождения, указывающее на репозиторий **GitHub**.

## Заявление прав на приложение

При заявлении прав регистрация вашего приложения назначается рабочему пространству Twenty, которое будет им управлять. Заявление прав на приложение доступно всем рабочим пространствам. Для получения прав через вкладку **Apps** в **Settings > Developers** вашей роли необходимы разрешения **Workspace Apps** и **Developers**.

Право собственности определяется для каждого экземпляра Twenty: заявление прав в Twenty Cloud не заявляет права на приложение на отдельном самостоятельно размещённом сервере. Другие рабочие пространства в том же экземпляре устанавливают ваше приложение, не заявляя права на него самостоятельно.

### Перед заявлением прав

* Опубликуйте пакет из **общедоступного репозитория GitHub**, используя GitHub Actions и [доверенную публикацию npm с подтверждением происхождения](#ci-publishing). Версия, импортированная в каталог Twenty, должна содержать аттестацию происхождения.
* Добавьте ключевое слово `twenty-app` в `package.json` и дождитесь [синхронизации каталога](#how-marketplace-discovery-works).
* Выберите рабочее пространство, которому будет принадлежать приложение. Для приложений с серверными маршрутами это рабочее пространство также запускает и оплачивает общий резолвер.
* Войдите в GitHub под **личной учётной записью, которой принадлежит исходный репозиторий**, или как **владелец организации**, которой он принадлежит. Одного доступа соавтора репозитория или доступа сопровождающего пакета npm недостаточно.

### Закрепить через GitHub

1. В рабочей области предполагаемого владельца перейдите в **Настройки > Разработчики > Приложения** (`/settings/developers#apps`).
2. В разделе **Заявить права на приложение** введите точное имя пакета npm, включая его область видимости (например, `@your-org/twenty-app`), или `universalIdentifier` приложения.
3. Нажмите **Найти** и убедитесь, что результатом является ваше приложение. Если оно не найдено, нажмите **Синхронизировать каталог**, если эта кнопка доступна, дождитесь завершения синхронизации, а затем выполните поиск снова.
4. Нажмите **Заявить права с помощью GitHub** и авторизуйте Twenty. Для репозитория, принадлежащего организации, предоставьте доступ к этой организации в разделе GitHub **Доступ к организации**. Для личных репозиториев не требуется предоставлять доступ организации.
5. Вернувшись в Twenty, убедитесь, что приложение отображается в разделе **Мои приложения** с типом **NPM**. Откройте его и убедитесь, что в разделе **Распространение > Владение** указано **Заявлено этим рабочим пространством**.

Заявление прав не устанавливает приложение. Если приложение предоставляет серверные маршруты, завершите указанную ниже настройку до того, как другие рабочие пространства начнут зависеть от его вебхуков.

### Настройка серверных маршрутов

[Серверный маршрут](/ru/developers/extend/apps/logic/logic-functions#server-route-trigger) получает события для нескольких рабочих пространств по одному URL-адресу. Его резолвер запускается в **рабочем пространстве владельца** регистрации, а затем распределяет работу в соответствующее рабочее пространство, где установлено приложение.

1. Откройте приложение в разделе **Мои приложения** и заполните все обязательные **Переменные сервера** на вкладке **Конфигурация**.
2. В разделе **Распространение** нажмите **Посмотреть на маркетплейсе**, чтобы открыть страницу приложения и установить его в **рабочем пространстве владельца**. Вы можете открыть эту страницу ещё до появления приложения в поиске маркетплейса.
3. Зарегистрируйте URL-адрес серверного вебхука у своего провайдера и протестируйте событие из второго рабочего пространства, в котором установлено приложение. Проверьте журналы как резолвера, так и целевой функции.

<Warning>
  У незаявленного приложения или приложения, не установленного в рабочем пространстве владельца, нет
  обработчика маршрутов сервера для запуска. Запросы возвращают `404`
  (`LOGIC_FUNCTION_NOT_FOUND`), даже если приложение установлено в других
  рабочих пространствах. Эти приложения не отображаются в поиске маркетплейса, пока не будут заявлены, установлены
  в рабочем пространстве владельца и настроены со всеми необходимыми переменными сервера.
</Warning>

### Стоимость и доступность рабочего пространства владельца

Сведения о потреблении кредитов, ценах и выставлении счетов рабочему пространству см. в разделе [Как учитываются запуски логических функций](/ru/user-guide/billing/capabilities/credits#how-logic-function-runs-are-metered).

Удаление приложения из рабочего пространства владельца или удаление этого рабочего пространства удаляет общий резолвер и прерывает серверные вебхуки для всех установок в этом экземпляре.

### Владение после переноса репозитория

Перенос репозитория GitHub в другую личную учётную запись или организацию не передаёт и не удаляет существующее заявление прав в Twenty. Регистрация остаётся привязанной к рабочему пространству владельца. Сохраните тот же пакет npm и `universalIdentifier` приложения; смена рабочего пространства владельца Twenty требует отдельной передачи прав собственности.

### Устранение неполадок при заявлении прав

Если у вас возникли проблемы с заявлением прав на приложение, свяжитесь с нами в [Discord](https://discord.gg/cx5n4Jzs57) или [создайте задачу в GitHub](https://github.com/twentyhq/twenty/issues/new/choose).

<Accordion title="Конфигурация заявления прав GitHub для самостоятельного хостинга">
  Администратор сервера настраивает `APP_CLAIM_GITHUB_CLIENT_ID` и
  `APP_CLAIM_GITHUB_CLIENT_SECRET` с помощью OAuth-приложения GitHub. Установите для его URL обратного вызова авторизации
  значение вашего `SERVER_URL` с добавлением
  `/application-registration-claim/github/callback`, например
  `https://twenty.example.com/application-registration-claim/github/callback`.
  В Twenty Cloud эта конфигурация уже управляется для вас.
</Accordion>

## Видимость на маркетплейсе и проверка

Заявление прав устанавливает владение; оно не присваивает значок **Проверено**. По умолчанию на маркетплейсе включён фильтр **Только проверенные**. Чтобы найти приложения сообщества, перейдите в **Настройки > Приложения > Маркетплейс**, откройте фильтр и снимите флажок **Только проверенные**. Вы также можете поделиться прямой страницей установки приложения через **Мои приложения > ваше приложение > Распространение > Копировать ссылку для общего доступа**.

Метка «Проверено» сейчас применяется к приложениям, поддерживаемым Twenty, за безопасность и качество которых команда может поручиться. Сторонние приложения можно публиковать и устанавливать без этой метки.

Предложенный [контрольный список проверки сторонних маркетплейсов](/ru/developers/extend/apps/operations/marketplace-review)
находится в разработке. В нём описаны критерии проверки и доказательства для конкретных версий,
а не доступная программа сертификации.

Если ваше приложение по-прежнему отсутствует при отключённом фильтре **Только проверенные**, убедитесь, что синхронизация каталога завершена, все обязательные серверные переменные заполнены и настройка серверных маршрутов завершена.

После публикации приложения (npm) или его развертывания (tarball) рабочие пространства могут установить его через интерфейс.

Перейдите на страницу **Настройки > Приложения** в Twenty, где можно просматривать и устанавливать как приложения из маркетплейса, так и развернутые через tarball.

Вы также можете устанавливать приложения из командной строки:

```bash filename="Terminal"
twenty app install
```

<Note>
Сервер при установке применяет версионирование semver, аналогичное правилам при развёртывании:

* Установка той же версии, которая уже установлена в вашем рабочем пространстве, отклоняется с ошибкой `APP_ALREADY_INSTALLED`.
* Установка версии ниже текущей отклоняется с ошибкой `CANNOT_DOWNGRADE_APPLICATION`.

Чтобы установить более новую версию, сначала разверните или опубликуйте её, затем снова выполните `twenty app install`.

</Note>
