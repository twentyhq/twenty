## Обзор

Локальная разработка приложения строится вокруг **синхронизации**: CLI пересобирает ваш манифест, а сервер применяет только разницу между ним и метаданными, которые уже есть в вашем рабочем пространстве. На этой странице описано, какую команду выбрать, как читать, что изменила синхронизация, и что делать — по шагам — когда локальное состояние выглядит несогласованным.

## Какую команду и когда использовать

<Note>
  Для повседневной локальной разработки вам почти всегда нужна команда `twenty app dev`.
  Развертывание и публикация предназначены для выпуска релизов, **а не** для локального
  цикла разработки.
</Note>

| Вы хотите…                                                       | Команда                        | Заметки                                                                                                                                                                        |
| ---------------------------------------------------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Выполнять локальные итерации с синхронизацией в реальном времени | `twenty app dev`               | Отслеживает ваши файлы и синхронизирует при каждом изменении.                                                                                                                  |
| Выполнить одну синхронизацию и выйти (CI, скрипты, хуки)         | `twenty app apply`             | Одна сборка + синхронизация, затем завершение работы. Добавьте `--yes`, чтобы пропустить подтверждение разрушительных изменений.                                               |
| Предпросмотр изменений **без их применения**                     | `twenty app plan`              | Вычисляет и выводит diff; ничего не записывает.                                                                                                                                |
| Синхронизировать без удаления чего-либо                          | `twenty app apply --no-delete` | Только создаёт и обновляет: сущности, существующие в рабочей области, но отсутствующие в исходном коде, остаются без изменений. Также поддерживается командами `plan` и `dev`. |
| Повторно создать локальный исходный код из рабочей области       | `twenty app pull`              | **Экспериментальная функция.** Записывает установленное приложение обратно в файлы определения. См. ниже.                                                                      |
| Удалить приложение из рабочего пространства                      | `twenty app uninstall`         | Добавьте `--yes`, чтобы пропустить запрос подтверждения.                                                                                                                       |
| Отправить на сервер tar-архив                                    | `twenty app publish --private` | Требуется **строго более высокая** версия в `package.json` — см. [Публикация](/ru/developers/extend/apps/operations/publishing).                                                  |
| Опубликовать на маркетплейсе (npm)                               | `twenty app publish`           | —                                                                                                                                                                              |
| Установить / обновить развернутую версию                         | `twenty app install`           | Устанавливает версию, которая сейчас развернута.                                                                                                                               |

### Для локальной синхронизации не нужно повышать версию

Правило строго возрастающей `version` (`VERSION_ALREADY_EXISTS` при deploy, `APP_ALREADY_INSTALLED` / `CANNOT_DOWNGRADE_APPLICATION` при install) применяется к **`twenty app publish` / `twenty app install`** — пути релизов. `twenty app dev` синхронизирует ваш манифест на месте и никогда не требует изменения версии, поэтому вам не нужно трогать `package.json`, чтобы выполнять итерации. Если вы ловите себя на том, что поднимаете версию, чтобы протестировать локальное изменение, значит вы используете релизный путь, когда вам нужен цикл разработки (dev loop).

## Чтение вывода синхронизации

Каждая синхронизация выводит изменения метаданных, которые она применила (или применила бы, с `plan`), в стиле Terraform — по одному блоку на сущность с её атрибутами, затем строку с итогами:

```text filename="Terminal"
  # objectMetadata "rocket" will be created
  + icon          = "IconRocket"
  + labelSingular = "Rocket"
  + ...

  # fieldMetadata "launchedAt" will be updated
  ~ isNullable = false -> true

Plan: 2 to add, 1 to change, 1 to destroy.

✓ Synced My App (4 files)
```

Это ваша первая диагностическая точка: она показывает, какие именно объекты, поля и макеты изменились, чтобы вы могли подтвердить, что синхронизация сделала то, что вы ожидали, до проверки в интерфейсе.

Разрушительные изменения (`to destroy`) перечисляются вместе с тем, что они удаляют (например, `objectMetadata "auditNote" — drops the table and all its rows`), и требуют интерактивного подтверждения или `--yes` в скриптах.

При синхронизации удаляются все сущности, принадлежащие вашему приложению, которые больше не объявлены в исходном коде. Когда план включает удаления, это указано и приведена ссылка на `--no-delete`, который делает синхронизацию аддитивной: применяются создания и обновления, ничего, отсутствующего в вашем источнике, не удаляется, а компонент настроек и привязки обработчика удаления приложения остаются без изменений, если ваш источник их не объявляет. Используйте этот параметр, когда исходный код намеренно неполный, например при внедрении приложения, созданного в пользовательском интерфейсе.

Когда синхронизация завершается с ошибкой на одной сущности, в сообщении указываются проблемная сущность и её `universalIdentifier`, например:

```text
Migration action 'create' for 'fieldMetadata' (universalIdentifier: 2020...4337) failed
```

Используйте этот идентификатор, чтобы найти сущность в своем манифесте (и, при необходимости, в рабочем пространстве), вместо того чтобы гадать, какая из них конфликтует.

## Предпросмотр изменений (plan)

`twenty app plan` собирает ваш манифест, запрашивает у сервера план миграции и выводит его — **без применения чего-либо**. Это безопасный способ ответить на вопрос «что изменит эта синхронизация?» до того, как вы на неё согласитесь.

```bash filename="Terminal"
twenty app plan
```

```text filename="Terminal"
Building manifest...
Computing metadata plan (read-only, nothing will be applied)...

  # fieldMetadata "crewCapacity" will be created
  + ...

Plan: 1 to add, 1 to change, 0 to destroy.

✓ Plan complete for My App — no changes were applied
```

План:

* **Ничего не записывает** — ни миграции метаданных, ни обновления записи приложения, ни изменений ролей/вкладок по умолчанию, ни генерации API‑клиента.
* Возвращает **тот же diff**, который применит реальная синхронизация, чтобы вы могли заранее просмотреть создаваемые/обновляемые/удаляемые сущности.
* Полезен перед рискованным изменением, при проверке изменения, сгенерированного ИИ, или в скрипте, который должен завершаться с ошибкой, если вот-вот будет применено неожиданное изменение.

<Note>
  План предварительно показывает только изменения **метаданных**. Это также работает для приложения, которое
  никогда не синхронизировалось: сервер сравнивает манифест с пустым приложением,
  поэтому план перечисляет всё, что создал бы ваш исходный код.
</Note>

## Возврат установленного приложения к исходному коду

<Warning>
  `twenty app pull` является **экспериментальной** командой. Сейчас она охватывает лишь часть приложения,
  формат её вывода может меняться между релизами, и она перезаписывает
  файлы, определяющие извлекаемые ею сущности. Она восстанавливает опубликованные переводы
  в `locales/`, сохраняя записи, исходные строки которых ещё отсутствуют в вашем дереве,
  в `locales/compiled/`, чтобы отправка не привела к их потере. Зафиксируйте изменения
  перед её запуском и просмотрите diff.
</Warning>

`twenty app pull` — это операция, обратная `apply`: она считывает приложение из рабочего пространства и записывает его обратно в виде файлов определений.

```bash
twenty app pull --universal-identifier <universalIdentifier>
```

Для pull нужен существующий проект — сначала создайте его каркас с помощью `twenty app init`, затем выполните pull в него. Без `--universal-identifier` pull выбирает приложение, объявленное в вашем локальном файле `defineApplication()`. Если `--universal-identifier` указывает другое приложение, а не то, которое объявлено в вашем проекте, pull откажется от выполнения, вместо того чтобы оставить два приложения в одном дереве: выполните pull этого приложения в отдельный каталог. Если в проекте есть файл приложения, идентификатор которого невозможно прочитать, обычно потому, что зависимости не установлены, pull также отказывается выполнять операцию и просит сначала запустить `yarn install`. Добавьте `--verbose`, чтобы развернуть разделы охвата в отчёте: тогда в них будет указано до 20 идентификаторов для каждого типа метаданных, а не только итоговые значения.

**Что записывается:**

* конфигурация приложения;
* объекты со встроенными полями;
* поля, добавленные вашим приложением к объектам, которыми оно не владеет;
* авторские индексы;
* флаги разрешений, объявленные вашим приложением, в виде файлов `definePermissionFlag()`;
* роли с разрешениями объектов, разрешениями полей, предикатами разрешений на уровне строк и группами, а также с флагами разрешений, заданными непосредственно в них. Роль по умолчанию вашего приложения записывается с помощью `defineApplicationRole()`. Разрешение объекта или поля, идентификатор которого определяется сборкой, записывается без него. Если роль по умолчанию не является одной из собственных ролей вашего приложения, как для приложения рабочей области Custom application, конфигурация приложения вместо этого сохраняет `defaultRoleUniversalIdentifier`;
* представления с их полями, группами полей, фильтрами, группами фильтров, сортировками и встроенными группами;
* поля представлений, добавленные вашим приложением в представления, которыми оно не владеет, в виде отдельных файлов `defineViewField()`;
* макеты страниц с их вкладками и виджетами в строке;
* вкладки, которые ваше приложение добавило в макеты страниц, ему не принадлежащие, в виде отдельных файлов `definePageLayoutTab()`;
* элементы меню навигации, включая файлы и папки `defineNavigationMenuItem()`;
* виджеты, которые ваше приложение добавило на вкладки, которыми оно не владеет, в виде отдельных файлов `definePageLayoutWidget()`;
* воркфлоу в виде файлов `defineWorkflow()`, когда их сохранённая версия совпадает с той, которую записала последняя синхронизация;
* навыки в виде файлов `defineSkill()`;
* агенты в виде файлов `defineAgent()` с их триггерами и ролью, с которой их связывает ваше приложение;
* опубликованные переводы в виде `locales/\<locale>.json`, чтобы `strings pull` мог считывать их из извлеченных метаданных и исходного текста, и `locales/compiled/\<locale>.json` для остальных.

Каждая сущность помещается в файл, который уже её определяет, поэтому повторный pull перезаписывает только то, что изменилось на сервере. Файл также перезаписывается, если в нем используется другая функция define, чем та, которую записала бы команда pull, например роль, которая стала или перестала быть ролью по умолчанию. Новые сущности размещаются рядом с существующими файлами того же типа, а сгенерированное имя, которое совпало бы с несвязанным файлом, уточняется вместо его перезаписи.

**Что не записывается:**

* **Еще не экспортировано** — элементы меню команд и меню настроек, функции логики и фронтенд-компоненты, поставщики подключений, переменные приложения, общедоступные ресурсы, типы активности временной шкалы и сохраненный исходный код ваших функций.
* **Определяется движком** — системные поля, отношения по умолчанию, представления по умолчанию и поддерживающие их индексы, а также макеты страниц по умолчанию каждого объекта. Сервер пересоздаёт их при apply. Объект всё ещё может указывать свой идентификатор метки на одно из них, как это делают объекты-связки, созданные в пользовательском интерфейсе; указатель записывается, а сборка разрешает его без добавления поля.
* **Размещено в представлении по умолчанию или внешнем представлении** — фильтры, группы фильтров, сортировки, группы и группы полей, добавленные в представление движка по умолчанию или в представление, принадлежащее другому приложению, пока не имеют исходной формы и фиксируются в отчёте. Добавленные туда поля представления записываются как отдельные файлы, поскольку идентификатор представления известен.
* **Размещённые в макете страницы по умолчанию или чужом макете страницы** — вкладки и виджеты, добавленные в макет страницы по умолчанию механизма или в макет, принадлежащий другому приложению, записываются как отдельные файлы `definePageLayoutTab()` и `definePageLayoutWidget()`, поскольку идентификатор, к которому они привязываются, известен.
* **Виджеты, которые экспорт пока не может включить** — в любом макете, включая ваш собственный, виджет устаревшего типа `VIEW`, виджет, отображающий один из собственных компонентов фронтенда или элементов меню команд вашего приложения, либо виджет без позиции для режима макета его вкладки отображается в отчёте, а макет или вкладка записывается без него.
* **Воркфлоу, которые экспорт пока не может перенести** — воркфлоу, изменённый в конструкторе воркфлоу после последней синхронизации, созданный в рабочей области, системный или приватный воркфлоу, воркфлоу с шагом Code или сообщением чата, которые воркфлоу приложений не поддерживают, либо с шагом электронной почты или календаря, которые экспорт пока не переносит, а также воркфлоу, вызывающий действие воркфлоу другого приложения, помечаются и остаются на месте. Пользовательское приложение рабочей области является исключением в последнем случае: его воркфлоу могут вызывать действия любого приложения, поэтому они извлекаются.
* **Агенты и навыки, которые экспорт пока не может перенести** — об агентах и навыках, созданных в рабочем пространстве, а не вашим приложением, о деактивированном навыке и об агенте с конфигурацией модели или привязанном к роли, которую извлечение не записывает, сообщается, и они остаются на месте.
* **Состояние среды выполнения рабочего пространства** — назначения ролей участникам и API-ключам, вебхуки, навигация для каждого пользователя и элементы навигации, закрепленные за записью; все это намеренно исключено.
* **Принадлежит другому приложению** — указывается в отчёте, но не извлекается.

В отчёте по завершении операции извлечения всё это перечислено, сгруппированное по типу и причине. Всё, что в отчёте указано как не записанное, по-прежнему находится в вашем рабочем пространстве, поэтому отправляйте извлечённое дерево обратно с помощью `twenty app apply --no-delete`, пока не будут охвачены отсутствующие типы. `twenty app apply` с удалением удалил бы их, а `twenty app plan` точно перечисляет, какие именно.

**Локальное для рабочей области состояние.** Сущность, деактивированная в рабочей области, записывается как активное определение, а переопределения, применённые рабочей областью к сущности, например переименованная метка, не записываются. В отчёте эти строки перечислены в разделе «Записано без локального состояния рабочей области». Повторное применение дерева к той же рабочей области не изменяет это состояние; в другой рабочей области сущность будет активной и без переопределений.

**Базовый файл.** Pull записывает извлечённые данные в `.twenty/pull-base.json`, который игнорируется Git и создаётся отдельно для каждой рабочей копии. Именно с этим файлом последующий pull сравнивает данные, чтобы не изменять файлы сущностей, которые не изменились, и удалить файл сущности, исчезнувшей из рабочего пространства. Рабочая копия без него просто записывает всё и ничего не удаляет.

## Лестница восстановления

Когда локальные метаданные выглядят неверно, действуйте поэтапно в следующем порядке и останавливайтесь, как только проблема решена. Каждый следующий шаг более разрушителен, чем предыдущий.

1. **Повторная синхронизация.** Снова выполните `twenty app apply`. Синхронизации идемпотентны — повторный запуск корректного манифеста безопасен и часто устраняет временный сбой.
2. **Предварительный просмотр плана.** Выполните `twenty app plan`, чтобы увидеть, что именно намеревается изменить следующая синхронизация, не применяя эти изменения.
3. **Прочитайте сообщение об ошибке.** Если синхронизация завершается с ошибкой, обратите внимание на тип метаданных и `universalIdentifier` в сообщении (см. выше) и найдите эту сущность в своем манифесте. Конфликт обычно указывает на дублированный или повторно используемый идентификатор.
4. **Удаление и повторная установка.** Выполните `twenty app uninstall`, затем снова синхронизируйте (`twenty app dev`). Это пересобирает метаданные приложения с нуля, сохраняя остальную часть вашего рабочего пространства нетронутой.
5. **Полный сброс (крайняя мера).** Сбросьте базу данных разработки Docker или репозитория, затем заново выполните начальное наполнение данными и синхронизацию.

<Warning>
  сброс базы данных разработки Docker или репозитория удаляет **все** данные
  в вашем локальном экземпляре — все рабочие пространства, записи и приложения. Используйте это только после того, как предыдущие шаги не помогли.
</Warning>

<Note>
  Столкнулись с ошибкой метаданных? Пожалуйста, [создайте issue](https://github.com/twentyhq/twenty/issues/new/choose) и приложите
  сообщение о сбое миграции (с типом метаданных и `universalIdentifier`),
  вывод `Metadata changes` из синхронизации и команды, которые вы запускали.
</Note>

## Избегайте одновременных синхронизаций в одном рабочем пространстве

Синхронизация применяет миграции метаданных. Запуск нескольких операций sync, deploy или install по отношению к **одному и тому же рабочему пространству одновременно** — например, из нескольких терминалов или при параллельных итерациях агентов ИИ — может перемешать эти миграции и оставить метаданные в частично примененном состоянии.

Сервер последовательно обрабатывает синхронизации для каждого рабочего пространства, чтобы предотвратить это, но вам всё равно следует пропускать чувствительные операции с метаданными через **один** процесс, а не запускать их параллельно. Если вы организуете разработку с несколькими агентами, направляйте их вызовы sync/deploy/install через одну очередь, чтобы в каждый момент времени выполнялась только одна операция.

## Как различать типы сбоев

Когда что‑то идёт не так, diff метаданных и именованные ошибки помогают определить, на каком этапе произошел сбой:

* **Ошибка сборки манифеста** — CLI завершается с ошибкой до синхронизации (`MANIFEST_BUILD_FAILED`, `TYPECHECK_FAILED`); исправьте исходный код приложения.
* **Ошибка принадлежности регистрации** — синхронизация отклоняется, поскольку `universalIdentifier` приложения принадлежит другой рабочей области или вообще не принадлежит ни одной рабочей области; см. [Принадлежность регистрации](/ru/developers/extend/apps/operations/publishing#registration-ownership).
* **Ошибка синхронизации / миграции** — сборка проходит успешно, но применение diff завершается сбоем с указанием сущности и `universalIdentifier`; исправьте конфликтующие метаданные.
* **Ошибка размера зависимостей** — синхронизация или установка завершается сбоем, потому что продакшен‑зависимости приложения (`dependencies`) слишком велики, чтобы их установить в качестве слоя среды выполнения (`LOGIC_FUNCTION_DEPENDENCIES_SIZE_EXCEEDED`); перенесите пакеты, которые ваши логические функции не импортируют во время выполнения (UI-библиотеки, инструменты разработки), в `devDependencies`.
* **Выполняется отложенная миграция** — синхронизация отклонена, поскольку фоновая миграция модели данных из предыдущей синхронизации всё ещё выполняется (`DEFERRED_WORKSPACE_MIGRATION_ACTIONS_IN_PROGRESS`); дождитесь её завершения, затем повторите синхронизацию.
* **Ошибка выполнения кода приложения** — синхронизация проходит успешно, но ваши логические функции или компоненты ведут себя неправильно во время выполнения; проверьте [журналы функций](/ru/developers/extend/apps/operations/cli).
* **Локальное состояние экземпляра** — ни один из вышеперечисленных пунктов не подходит, и рабочее пространство всё ещё выглядит неправильно; двигайтесь вниз по лестнице восстановления.
