## Resumen

Los **objetos** personalizados son nuevos tipos de registro que tu aplicación añade a un espacio de trabajo — Tarjeta postal, Factura, Suscripción, cualquier cosa específica de tu dominio. Cada objeto declara su esquema (campos, relaciones, valores predeterminados) y un identificador universal estable que se mantiene a través de sincronizaciones e implementaciones.

```ts src/objects/post-card.object.ts
import { defineObject, FieldType } from 'twenty-sdk/define';

enum PostCardStatus {
  DRAFT = 'DRAFT',
  SENT = 'SENT',
  DELIVERED = 'DELIVERED',
  RETURNED = 'RETURNED',
}

export default defineObject({
  universalIdentifier: '54b589ca-eeed-4950-a176-358418b85c05',
  nameSingular: 'postCard',
  namePlural: 'postCards',
  labelSingular: 'Post Card',
  labelPlural: 'Post Cards',
  description: 'A post card object',
  icon: 'IconMail',
  fields: [
    {
      universalIdentifier: '58a0a314-d7ea-4865-9850-7fb84e72f30b',
      name: 'content',
      type: FieldType.TEXT,
      label: 'Content',
      description: "Postcard's content",
      icon: 'IconAbc',
    },
    {
      universalIdentifier: 'c6aa31f3-da76-4ac6-889f-475e226009ac',
      name: 'recipientName',
      type: FieldType.FULL_NAME,
      label: 'Recipient name',
      icon: 'IconUser',
    },
    {
      universalIdentifier: '95045777-a0ad-49ec-98f9-22f9fc0c8266',
      name: 'recipientAddress',
      type: FieldType.ADDRESS,
      label: 'Recipient address',
      icon: 'IconHome',
    },
    {
      universalIdentifier: '87b675b8-dd8c-4448-b4ca-20e5a2234a1e',
      name: 'status',
      type: FieldType.SELECT,
      label: 'Status',
      icon: 'IconSend',
      defaultValue: `'${PostCardStatus.DRAFT}'`,
      options: [
        {
          value: PostCardStatus.DRAFT,
          label: 'Draft',
          position: 0,
          color: 'gray',
        },
        {
          value: PostCardStatus.SENT,
          label: 'Sent',
          position: 1,
          color: 'orange',
        },
        {
          value: PostCardStatus.DELIVERED,
          label: 'Delivered',
          position: 2,
          color: 'green',
        },
        {
          value: PostCardStatus.RETURNED,
          label: 'Returned',
          position: 3,
          color: 'orange',
        },
      ],
    },
    {
      universalIdentifier: 'e06abe72-5b44-4e7f-93be-afc185a3c433',
      name: 'deliveredAt',
      type: FieldType.DATE_TIME,
      label: 'Delivered at',
      icon: 'IconCheck',
      isNullable: true,
      defaultValue: null,
    },
  ],
});
```

## Puntos clave

* El `universalIdentifier` debe ser único y estable entre implementaciones.
* Cada campo requiere `name`, `type`, `label` y su propio `universalIdentifier` estable.
* La matriz `fields` es opcional: puedes definir objetos sin campos personalizados.
* `openRecordIn` establece dónde se abren los registros de este objeto al hacer clic: `ObjectOpenRecordIn.USER_CHOICE` (el valor predeterminado, que sigue la preferencia de cada miembro del espacio de trabajo en Settings → Experience), `ObjectOpenRecordIn.SIDE_PANEL` o `ObjectOpenRecordIn.RECORD_PAGE`. Fíjalo en `RECORD_PAGE` para los registros que necesitan una página completa para ser utilizables, como ocurre con los flujos de trabajo y los paneles, o en `SIDE_PANEL` para los registros que solo tienen sentido como un panel rápido, como los eventos del calendario.
* `writability` controla quién puede escribir registros del objeto en general, antes de que se apliquen los permisos por rol: `MetadataWritability.OPEN` (predeterminado — lo deciden los roles del espacio de trabajo), `MetadataWritability.APPLICATION` (solo las funciones de lógica de tu aplicación pueden crear, actualizar o eliminar registros; usa esto para objetos de configuración cuyos registros definen el comportamiento, de modo que los miembros del espacio de trabajo con amplio acceso a registros no puedan editarlos a través de la API) o `MetadataWritability.SYSTEM` (reservado para datos gestionados por la plataforma). Las lecturas no se ven afectadas: esto se aplica en el lado del servidor, a diferencia de `isUIEditable`, que solo oculta las funcionalidades de la interfaz de usuario. También existe por campo, donde solo puede ser más restrictivo que el nivel del objeto.
* `readability` declara quién puede leer los registros del objeto: `MetadataReadability.OPEN` (el valor predeterminado; los roles del espacio de trabajo deciden), `MetadataReadability.PRIVATE` (solo las entidades principales con las que se compartió el registro), `MetadataReadability.INHERITED` (quien lea el registro principal), `MetadataReadability.APPLICATION` (solo las funciones lógicas de tu propia aplicación) o `MetadataReadability.SYSTEM` (datos administrados por la plataforma). Todas las políticas de legibilidad siempre se aplican.
* `readabilityParentFieldUniversalIdentifiers` va con `MetadataReadability.INHERITED`: los identificadores universales de los campos de relación que conducen a los registros padre.
  * Un campo de muchos a uno nombra el registro al que apunta la fila. Declarar un campo de una relación polimórfica abarca todos los destinos de esa relación.
  * Un campo de uno a muchos nombra un objeto secundario cuyas filas apuntan de vuelta al registro, como las filas de unión de una relación de muchos a muchos. El registro se puede leer entonces cuando al menos una de esas filas conduce a un registro legible: una nota sigue a las personas, empresas y oportunidades a las que la adjuntan los destinos de su nota.
  * Varios registros padre se combinan como una unión: basta con que uno de ellos sea legible.
  * Un padre concede acceso conforme a su política completa, la que se aplica a una consulta del padre: el permiso del lector sobre el objeto padre, las restricciones a nivel de fila de su función y la propia capacidad de lectura del padre. Un registro nunca se muestra a través de un padre que su lector no pudiera consultar. Las suscripciones, los webhooks, los flujos de trabajo y las funciones lógicas deciden qué alcanza un evento de un registro `INHERITED` conforme a esa misma política.
  * Las filas de uso compartido del propio registro conceden acceso exactamente igual que en un registro `PRIVATE`. Su creador recibe una cuando se crea el registro mientras está habilitado el uso compartido de registros, de modo que quien haya creado un registro siga viéndolo, y un registro cuyos campos padre estén todos vacíos sea visible para aquellos con quienes se compartió directamente.
  * Un objeto `INHERITED` que no nombra ningún campo principal utilizable se comporta como uno `PRIVATE`.
* `sharingReach` establece hasta qué punto se puede compartir por nombre un registro del objeto: `ObjectSharingReach.WORKSPACE` (el valor predeterminado: un registro puede compartirse con cualquier persona del espacio de trabajo, incluso alguien cuyo rol no pueda acceder al objeto o cuyo filtro de nivel de fila oculte el registro; solo obtiene ese registro, para verlo o editarlo) o `ObjectSharingReach.ROLE_ACCESS` (las comparticiones nunca van más allá de los permisos de rol y de nivel de fila). Elige `ROLE_ACCESS` para objetos confidenciales en los que ningún acceso debe significar ningún acceso. Los roles que pueden actualizar todos los ajustes ven todos los registros de un objeto `OPEN`, independientemente de sus restricciones de uso compartido; sus permisos de objeto y filtros de nivel de fila siguen aplicándose. Solo se aplica mientras el uso compartido de registros esté habilitado en el espacio de trabajo, y solo a objetos cuyos registros pueden compartirse: objetos `MetadataReadability.OPEN`, `PRIVATE` e `INHERITED` que no sean objetos del sistema. Los objetos `APPLICATION` y `SYSTEM` nunca se comparten.
* `disabledObjectPermissionActions` enumera los permisos de objeto que no se pueden conceder sobre el objeto: cualquiera de `'canReadObjectRecords'`, `'canUpdateObjectRecords'`, `'canSoftDeleteObjectRecords'` y `'canDestroyObjectRecords'`, las mismas marcas que un rol establece por objeto. No se puede guardar un permiso de objeto que conceda uno de ellos sobre este objeto; por ejemplo, `disabledObjectPermissionActions: ['canDestroyObjectRecords']` impide específicamente que se conceda a cualquier rol la acción de destruirlo. No cambia lo que pueden hacer los roles que conceden una acción sobre todos los objetos.
* `color` establece el color de acento del objeto en la IU. Omítelo y Twenty elegirá uno para el objeto.
* `imageIdentifierFieldMetadataUniversalIdentifier` nombra el campo cuyo valor se muestra como el avatar del registro. Omítelo para que Twenty elija el predeterminado.
* `isLabelSyncedWithName`, en un objeto o en un campo, mantiene el nombre de la API sincronizado con la etiqueta cuando esta se edita en Configuración. De forma predeterminada es `false`, por lo que una etiqueta renombrada deja el nombre sin cambios.
* `isSearchable: true`, en un campo, incluye sus valores en la búsqueda de texto completo del objeto (búsqueda global y el menú de comandos). Requiere que el propio objeto permita búsquedas y que el tipo de campo sea compatible con texto. Un valor omitido significa que no permite búsquedas, excepto en el campo identificador de etiqueta del objeto, que siempre permite búsquedas y no se puede excluir. Cada sincronización aplica el estado declarado, por lo que un campo cuya opción de búsqueda se active desde Configuración se revertirá en la siguiente sincronización de tu aplicación, a menos que el manifiesto lo declare.
* `isAuditLogged: false` en un campo evita que sus cambios aparezcan en la cronología del registro. De forma predeterminada es `true`, excepto en un campo `POSITION`, cuyos cambios aparecen en blanco en la cronología y nunca se registran. Establécelo en los campos que tu aplicación reescribe de forma programada, como una marca de tiempo del último contacto o una relación de acumulación, para que cada sincronización no agregue una fila de actividad a cada registro que modifique. Una actualización cuyo diferencial completo está compuesto por campos sin registro de auditoría no produce ninguna actividad en la cronología. Al igual que `isSearchable`, cada sincronización aplica el estado declarado.
* Los campos en línea definidos aquí **no** necesitan un `objectUniversalIdentifier`, ya que se hereda del objeto padre. Usa [`defineField()`](/es/developers/extend/apps/data/extending-objects) para añadir campos a objetos que no te pertenecen.
* Puedes generar nuevos objetos con `twenty app add object`, que te guía en la asignación de nombres, los campos y las relaciones. Consulta [Arquitectura → Generación de entidades](/es/developers/extend/apps/getting-started/scaffolding).

<Note>
  **Los campos base se añaden automáticamente.** Cuando defines un objeto personalizado,
  Twenty crea campos estándar como `id`, `name`, `createdAt`, `updatedAt`,
  `createdBy`, `updatedBy` y `deletedAt` por ti. No necesitas declararlos
  en tu matriz `fields`; solo tus campos personalizados. Puedes sobrescribir un
  campo predeterminado declarando uno con el mismo nombre, pero esto rara vez es una buena
  idea.
</Note>

## Tipos de campo

El conjunto completo de valores de `FieldType`, exportados desde `twenty-sdk/define`:

| Categoría                    | Tipos                                                                                                                                                                                                                                                                                                              |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Texto                        | `TEXT`, `RICH_TEXT`, `ARRAY` (de cadenas), `RAW_JSON`                                                                                                                                                                                                                                                              |
| Numérico                     | `NUMBER` (`universalSettings.dataType`: `'float'` / `'int'` / `'bigint'`), `NUMERIC` (precisión arbitraria), `RATING`, `POSITION`                                                                                                                                                                                  |
| Fechas                       | `DATE`, `DATE_TIME`                                                                                                                                                                                                                                                                                                |
| Selección                    | `BOOLEAN`, `SELECT`, `MULTI_SELECT`                                                                                                                                                                                                                                                                                |
| Compuesto                    | `FULL_NAME`, `ADDRESS`, `EMAILS`, `PHONES`, `LINKS` (`universalSettings.type`: `'url'` (predeterminado) / `'domain'` — un campo de dominio almacena el host sin más, por lo que `https://www.acme.com/careers` se escribe como `acme.com`, y se rechaza un valor que no sea un host), `CURRENCY`, `ACTOR`, `FILES` |
| Identificadores y relaciones | `UUID`, `RELATION`, `MORPH_RELATION` (ver [Relations](/es/developers/extend/apps/data/relations))                                                                                                                                                                                                                     |
| Sistema                      | `TS_VECTOR` (vector de búsqueda de texto completo, gestionado por el servidor)                                                                                                                                                                                                                                     |

Los tipos compuestos almacenan múltiples subcampos (por ejemplo, `FULL_NAME` = nombre + apellido; `CURRENCY` = `amountMicros` + `currencyCode`). `SELECT` y `MULTI_SELECT` requieren un arreglo `options` como en el ejemplo anterior.

### Selecciona opciones

Para `SELECT` y `MULTI_SELECT`, proporcione una matriz no vacía de objetos `options`. Cada opción tiene un `value`, un `label` y una `position`. Su `color` es opcional y toma de forma predeterminada el valor `gray` cuando se omite o es nulo.

Cuando se proporciona, `color` debe ser uno de los siguientes: `red`, `ruby`, `crimson`, `tomato`, `orange`, `amber`, `yellow`, `lime`, `grass`, `green`, `jade`, `mint`, `turquoise`, `cyan`, `sky`, `blue`, `iris`, `violet`, `purple`, `plum`, `pink`, `bronze`, `gold`, `brown`, `gray`.

Tanto `defineObject()` como `defineField()` devuelven errores de validación para colores no compatibles o entradas de opciones que son nulas, primitivas o matrices.

## Valores predeterminados

Los valores predeterminados de cadenas literales deben ir entre comillas simples **dentro** de la cadena — `defaultValue: "'Draft'"`, no `defaultValue: "Draft"`. Por eso el campo `status` anterior utiliza `` `'${PostCardStatus.DRAFT}'` ``.

Las cadenas sin comillas se reservan para valores predeterminados calculados, evaluados cuando se crea un registro:

* `'uuid'` — genera un UUID (para campos `UUID`)
* `'now'` — la marca de tiempo actual (para campos `DATE_TIME`)

La misma convención se aplica a los subcampos de tipo cadena de los valores predeterminados compuestos (por ejemplo, `{ source: "'MANUAL'" }` en un campo `ACTOR`) y a los valores de `SELECT`/`MULTI_SELECT`. Un valor predeterminado de tipo cadena literal dejado sin comillas genera una advertencia cuando se compila tu aplicación.

## Nulabilidad

`isNullable` controla si un campo acepta `NULL`. Su valor predeterminado es `true` — omítelo para campos opcionales. Configura `isNullable: false` para hacer que un campo sea obligatorio a nivel de base de datos.

Los cambios en `isNullable` se aplican en cada sincronización, incluidas las sincronizaciones que actualizan un campo existente; de este modo, puedes cambiar la nulabilidad de un campo editando el manifiesto y sincronizando de nuevo.

<Note>
  **Hacer que un campo existente no acepte valores nulos requiere un valor predeterminado.** Cuando
  cambies un campo a `isNullable: false`, también debes proporcionar un `defaultValue` no nulo. El valor predeterminado rellena cualquier fila `NULL` existente antes de que se aplique la restricción `NOT
    NULL`; sin él, la sincronización falla con `Default value
    cannot be null for non-nullable fields`. Los campos de relación y los campos `TS_VECTOR`
  siempre aceptan valores nulos, por lo que `isNullable` no tiene ningún efecto en ellos.
</Note>

```ts
{
  universalIdentifier: 'b1a7c0de-1234-4f00-9abc-000000000000',
  name: 'reference',
  type: FieldType.TEXT,
  label: 'Reference',
  isNullable: false,
  defaultValue: "'N/A'",
}
```
