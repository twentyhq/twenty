# Gelios — календарь и участники

Реализовано локально 14 октября 2026. На стенд не применялось.

## Интерфейс

Следующий этап добавил временную сетку и создание тренировок из UI: [создание занятий](gelios-session-creation.ru.md). Ниже сохранено описание первоначального этапа календаря.

Маршрут #gelios/calendar: недельный календарь с временем Europe/Moscow, переходами по неделям и кнопкой «Сегодня». Показывает существующие classSessions CRM; новые слоты пока создаются в CRM.

Клик открывает дату/время, статус, вместимость, действующих и отменённых участников, пакеты и события CRM.

- Добавить в будущую PLANNED/CONFIRMED тренировку с местами: выбрать клиента и активный GROUP_PACKAGE/PERSONAL подходящего формата, покрывающий дату. Команда создаёт BOOKED, RESERVE(-1), обновляет счётчики и BOOKING_CREATED.
- Убрать — подтверждённая отмена студией, не удаление. Команда сохраняет CANCELLED_BY_STUDIO, связанный RELEASE(+1), счётчики и BOOKING_CANCELLED. Это не клиентская поздняя/своевременная отмена.
- Завершённые/прошедшие тренировки только для просмотра. ATTENDED, SPLIT и PAYG не отменяются обычной командой; история списаний не стирается.

## API и журнал

KateFitNotes: POST /api/v1/studio/bookings/create → POST /s/studio/bookings/create; POST /api/v1/studio/bookings/cancel → POST /s/studio/bookings/cancel. Требуются JWT KateFitNotes, UUID идентификаторов, idempotencyKey; отмена требует cancelledAt с часовым поясом. API-ключ только на сервере. GET /api/v1/studio/records/events читает studioEvents.

Успешные booking/cancel больше не проглатывают ошибку журнала. recordBookingEvent создаёт детерминированный UUID v5 от bookingId и типа действия; существующее событие сверяется по связям/результату. Повтор не создаёт второй успешный event.

Это не общая транзакция: бизнес-изменение может сохраниться до ошибки журнала. UI сохраняет тело/ключ в sessionStorage, перечитывает CRM и предлагает повтор. Повтор восстанавливает журнал без второго RESERVE/RELEASE. Незавершённые операции блокируют новые до повтора либо явной ручной проверки/сброса.

Отказы до бизнес-действия по-прежнему используют best-effort OPERATION_FAILED: недоступность CRM не позволяет гарантировать запись неудачной попытки в ней.

Дополнительные проверки CRM: нельзя записать того же активного участника новым ключом; исключены SPLIT из обычного добавления/отмены; для новой записи проверяются активация и срок пакета. Прежние проверки владения/баланса/слота сохраняются.

## Проверки

- 68 CRM tests; typecheck, lint и форматирование.
- 59 API/settings tests, 3 DB-зависимых пропущены.
- 22 UI tests, JS syntax check.
- Headless Chrome: календарь/карточка, добавление, потерянный ответ, reload/повтор прежнего ключа, событие, отмена/возврат, событие, read-only завершённое занятие, mobile 390px. Все API замоканы, реальная CRM не изменялась.
- Desktop/карточка/mobile скриншоты просмотрены.

Браузерный тест: npm --prefix ui run test:browser:calendar, с Playwright и локальным UI по умолчанию 127.0.0.1:5184. PLAYWRIGHT_MODULE и UI_SMOKE_CHROME задают имеющуюся установку Playwright/Chrome.

## Выпуск на stage

1. Проверить plan/apply katfit-studio; вместе с командами нужен UNIQUE(booking, transactionType) из первого этапа.
2. Пересобрать отдельно API и UI KateFitNotes: одного UI недостаточно.
3. Проверить права CRM-приложения/ключа на studioEvents, чтение и запись.
4. На выделенных fixtures проверить BOOKED/RESERVE/event, повтор, CANCELLED_BY_STUDIO/RELEASE/event. Production не использовать для smoke.

Риск разных конкурентных запросов на последнее место/посещение не закрыт: SDK-мутации без общей DB-транзакции/блокировки. Подтверждено последовательное восстановление, не многопользовательская конкуренция. Правки прошлых посещений и правила клиентской отмены остаются отдельной задачей.
