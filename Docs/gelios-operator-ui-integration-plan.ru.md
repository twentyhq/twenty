# Интеграция операторского UI KateFitNotes со Studio Gelios / Twenty

Дата аудита: 14 октября 2026. Проверенная версия CRM: `39a44f699f`.
Статус: план реализации. По [аудиту API на staging](gelios-api-readiness-audit.ru.md) чтение доступно и 15 HTTP функций развёрнуты, но запись из внешнего UI пока не готова: отсутствует проверенный actor-контекст и выявлены дефекты повторов бронирования/отмены.

Обновление макетов: после исходной инвентаризации дорисованы отдельные экраны `GELIOS · 04–25`, а форма `03` приведена к полям клиента/пакета, причины и источника сведений. Ниже исходная таблица покрытия фиксирует состояние на момент первого аудита; её замечания о недостающих экранах закрыты отрисовкой, но не реализацией API или фронта.

## Вывод

CRM уже содержит модель студии и команды продажи пакета, внесения прошедшего занятия, бронирования, отмены, оплаты по факту и работы со сплитами. Внешний UI можно подключить к ним через серверный адаптер. Полный набор операторских действий текущими макетами Gelios не покрыт. Есть также бизнес-операции, для которых доступны CRUD и внутренний компонент CRM, но нет отдельной безопасной команды для внешнего UI.

Первый релиз: поиск/создание клиента → продажа оплаченного пакета → внесение прошедшего занятия → просмотр посещений, списаний и остатка. Следующий релиз: расписание, будущие записи, отмены, оплата по факту и сплиты. Возвраты, коррекции, заморозка и отработки требуют отдельной проработки команд.

## Что проверено и границы проверки

- Исходники `packages/twenty-apps/internal/katfit-studio/src`: объекты, HTTP logic functions, handlers и внутренние front components.
- Реализация универсального REST API Twenty и передача контекста пользователя в route trigger.
- `KateFitNotes_telegram/ui/src/app.js`, `api.js`, документация API и инвентаризация источников данных.
- Все верхнеуровневые экраны `pencil.pen` и тексты четырёх Gelios-макетов прочитаны через MCP Pencil. В этом аудите макеты не изменялись.
- Через подключённый `twenty_stage` выполнены только чтения: каталог показывает студийные объекты и CRUD; выборки активных продуктов и пакетов успешны. В данном workspace найдено 5 активных продуктов, 1 активный пакет, 0 операций `CONSUME`. Это проверка доступности чтения, не финансовая сверка и не инвентаризация production.
- HTTP POST-команды не вызывались: аудит не создавал клиентов, оплат, записей или списаний. Наличие команды в коде не доказывает её deployment или доступность с credentials внешнего UI. HTTP smoke-проверки и проверка actor-контекста остаются обязательным этапом на staging.

Старые feature-документы местами описывают команду списания как будущую. Для статуса реализации здесь приоритет отдан текущим handlers и README приложения.

## Архитектура и источник данных

```text
KateFitNotes UI
  ├─ Terfit → существующий /api/v1 → FastAPI → Kate_fitness
  └─ Gelios → новый /api/v1/studio → серверный CRM-адаптер
                                      ├─ чтение/профиль → Twenty REST / GraphQL
                                      └─ бизнес-команды → Twenty /s/studio/...
```

Для Terfit источник правды остаётся `Kate_fitness`; CRM-зеркало личных тренировок не превращать в источник записи. Для Gelios источник правды — студийные объекты Twenty. Переключатель выбирает контур и сбрасывает его черновики/кэш; numeric ID клиента Terfit и UUID Person Gelios не взаимозаменяемы. Не выполнять двойную запись одной операции в обе системы.

Предпочтительно расширить существующий FastAPI новым studio-router и CRM-client, сохранив текущий `/api/v1` контракт. API-ключ CRM хранить на сервере. Адаптер проверяет оператора, нормализует ответы, пагинацию, даты и ошибки; бизнес-расчёты баланса остаются в CRM. Браузеру не выдавать общий CRM API-ключ.

Решение по авторизации (14 октября 2026): пользователь согласовал серверный API-ключ без обязательного автора. KateFitNotes хранит CRM_API_KEY только на backend. Команда attendance локально принимает отсутствие userWorkspaceId и сохраняет recordedBy=null; HTTP route остаётся isAuthRequired=true. Права ключа проверяет Twenty. Передавать recordedBy/actorId из браузера нельзя. На исходном staging ещё действует ACTOR_REQUIRED до выпуска обновлённой команды.

## Матрица действий и API CRM

Маршруты команд в исходниках объявлены как `/studio/...`; существующие внутренние компоненты вызывают их с префиксом `/s`. В таблице указан полный клиентский путь. Все эти команды требуют авторизации. REST Twenty обслуживается под `/rest`; имена объектов взяты из текущих object definitions. Развёрнутую схему, фильтры и разрешения проверить на staging перед фиксацией внешнего контракта.

## Контракты первого релиза

### Продажа пакета

Источник: `src/logic-functions/utils/package-payment.ts`.

Обязательные поля: `personId`, `productId`, `paidAt`, `amount`, `paymentMethod` (`CASH|SBP|CARD`), `idempotencyKey`. Дополнительные: `externalId`, `fiscalReceiptId`.
`amount` — сумма в денежных единицах; цена продукта в CRM хранится как `amountMicros` (1 единица = 1 000 000 micros). Команда проверяет совпадение суммы с ценой, действующую версию продукта, дату оплаты не в будущем и положительное число посещений. Произвольные скидки/количество из текущей формы Terfit сюда переносить нельзя.

Успех: `success`, `duplicate`, `paymentId`, `membershipId`, `transactionId`, `visitsAvailable`. Ошибка: `success:false`, `code`, `message`, HTTP status. UI после результата перечитывает пакет и оплату.

### Внесение прошедшего занятия

Источник: `src/logic-functions/utils/past-attendance.ts` и соответствующий handler.

Обязательные поля: `personId`, `membershipId`, `startsAt`, `endsAt`, `reason`, `source`, `idempotencyKey`. Опциональные: `existingClassSessionId`, `sourceDetails`, `previewOnly`. Источник: `TRAINER|ATTENDANCE_LOG|CLIENT|ADMIN|OTHER`; для OTHER нужно пояснение.

Начало/окончание должны быть в прошлом. Handler выводит окончание из длительности продукта и проверяет оплаченный пакет, принадлежность клиенту, действие на дату занятия, исторический баланс, согласованность журнала и отсутствие дубликата. Формат берётся из продукта; произвольного `trainerId` или редактируемого статуса в контракте нет.

1. Выбрать клиента, затем конкретный пакет и дату/время.
2. Ввести причину внесения и источник сведений.
3. Вызвать ту же команду с `previewOnly:true`: показать серверные `visitsAvailable` и `visitsAfter`.
4. Подтвердить с тем же содержимым и стабильным ключом, `previewOnly:false`.
5. Показать связанные `bookingId`, `classSessionId`, `transactionId` и актуальный остаток. Повтор после timeout использует прежний ключ.

Команды выполняют несколько мутаций через SDK без общей транзакции. Идемпотентное восстановление снижает риск дублей, но не обеспечивает all-or-nothing. Нужны staging-тесты с промежуточным отказом и параллельным списанием последнего посещения. Не изображать любой сетевой timeout как окончательный отказ и не генерировать новый ключ при повторе.

Дата рождения, цель занятий, ограничения и назначенный тренер из карточки клиента требуют отдельной проверки метаданных Person: в проверенных студийных field definitions соответствующий набор не подтверждён. Не сохранять их в случайные поля; согласовать схему или показывать только подтверждённые поля. Для истории нескольких пакетов отображать оплачено/зарезервировано/списано/доступно, а не единственный прогресс «5 из 8».

## План реализации

1. **Зафиксировать staging-контракт.** Проверить применённую версию katfit-studio, REST/OpenAPI/GraphQL и HTTP triggers; выполнить чтения products/people/memberships/bookings/transactions. Проверить серверный API-ключ команды attendance и отсутствие обязательного автора. Результат: таблица маршрут → schema → роль → staging smoke result. Пока этот пункт не закрыт, не считать POST-ready.
2. **Дорисовать P0 через MCP Pencil.** Привести attendance к контракту, добавить клиента, продажу пакета, журнал списаний и общие состояния. Все четыре базовых действия должны иметь полный путь от ввода до результата. Проверить длинные имена, несколько пакетов, нулевой остаток и ошибку сети.
3. **Серверный адаптер KateFitNotes.** Новые настройки `CRM_BASE_URL`, серверные credentials и идентификация оператора; отдельный CRM-client; studio routes и единый error mapping. Предлагаемые, ещё не существующие routes: GET/POST `/api/v1/studio/clients`, GET/PATCH `/clients/{id}`, GET `/products`, GET `/memberships`, GET `/bookings`, GET `/transactions`, POST `/package-payments/confirm`, POST `/attendance/record-past`. Все пути после первого подразумевают тот же studio-префикс. Фильтры ограничены allowlist, страницы ограничены по размеру; адаптер не проксирует произвольный CRM URL.
4. **Контур Gelios в UI.** Разделить состояние и API-клиенты по workspace, добавить навигацию клиентов/пакетов/посещений/списаний. Реализовать поиск, P0 формы, preview, стабильный idempotencyKey и обновление данных после записи. Существующий `Api` сейчас обращается только к `/api/v1`, а `load()` загружает сущности Terfit: Gelios там не реализован.
5. **Проверить цепочку P0.** На тестовом клиенте: продажа → GRANT → preview → attendance → CONSUME → новый остаток → история. Повтор платежа/списания, перезагрузка после timeout, чужой пакет, старый/истёкший пакет, будущая дата, недостаточный остаток, дубликат, два параллельных запроса. Unit/contract тесты адаптера с mock CRM плюс staging integration и UI interaction tests. Чтение и replay не должны создавать новые операции.
6. **Расширить серверные команды для P1.** Добавить проведение существующей обычной брони (включая переход RESERVE → CONSUME), безопасное закрытие/отмену/перенос слота и проверки конкуренции. Для PAYG обеспечить attendance без списания пакета. Не заменять это CRUD статуса. Затем подключить существующие booking/PAYG/split команды и соответствующие макеты.
7. **Пилот и выпуск.** Раздельная feature flag Gelios, наблюдаемость ошибок/повторов/частичных операций без телефонов и credentials в логах. Проверенный staging build и тестовые результаты → ограниченный операторский пилот → production выпуск. Отключение UI не удаляет CRM-записи; незавершённые команды подлежат восстановлению с тем же ключом.

## Критерии готовности

- Для каждой доступной кнопки существует проверенный API-контракт и разрешение оператора; неподдерживаемые сценарии не выглядят работающими.
- Есть создание клиента, продажа пакета, завершённая тренировка и читаемый журнал её списания с переходом к исходным сущностям.
- GRANT/RESERVE/CONSUME различимы, список посещений не подменяет журнал операций.
- UI использует серверный preview/баланс; повтор не удваивает операции, ключ остаётся на сервере, автор необязателен.
- Пройдены staging-проверки частичного отказа и конкуренции; ограничения атомарности явно отражены в эксплуатационном процессе.
- Все P0 макеты и ошибки существуют в Pencil; сохранены исходные Terfit-сценарии и их источник данных.
