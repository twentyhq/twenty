# Тест-кейсы: запись с оплатой по факту

**Статус:** актуален для ветки `codex/pay-as-you-go-scheduling`.
**Область:** создание будущей записи без пакета, ожидаемая оплата, подтверждение
денег после посещения и отмена занятия.

## Подготовка

1. Выполнить `twenty plan`, проверить план и применить актуальную версию
   приложения в тестовом workspace через `twenty apply`.
2. Создать активный продукт категории `SINGLE` для группового формата и активный
   продукт `PERSONAL` для персонального формата. Указать цену и длительность.
3. Создать будущий групповой слот с вместимостью не менее двух мест и будущий
   персональный слот с вместимостью один. Формат каждого слота должен совпадать
   с соответствующим продуктом.
4. Подготовить клиента без активного пакета и клиента с подходящим активным
   пакетом и доступным посещением.

## Основные сценарии

| ID | Сценарий | Шаги | Ожидаемый результат |
| --- | --- | --- | --- |
| PAYG-00 | Черновик занятия с оплатой по факту | В часовой сетке начать создание нового занятия → «Добавить клиента» → выбрать «Оплата по факту» и подходящий продукт → выбрать клиента → сохранить занятие. | До сохранения клиент показан в составе черновика с пометкой «Оплата ожидается». После сохранения создаются слот, одна `Booking(BOOKED, EXPECTED)` и одна `Payment(EXPECTED)` с `bookingReferenceId`; место учтено во вместимости. |
| PAYG-00a | Переключение способа без потери выбора | В окне «Добавить клиента» выбрать одного или нескольких клиентов → переключить «По пакету» / «Оплата по факту» → выбрать подходящий продукт, если он нужен. | Выбранные клиенты остаются отмеченными. Переключатель определяет способ записи для добавляемой группы, но не удаляет выбор и не изменяет уже добавленных участников черновика. |
| PAYG-01 | Групповая запись без пакета | Открыть будущий групповой слот → «Добавить клиента» → выбрать «Оплата по факту» → выбрать разовый продукт → выбрать клиента без пакета → добавить. | Созданы `Booking(BOOKED)` и одна связанная `Payment(EXPECTED)`. Запись увеличивает заполненность слота на 1, баланс пакета клиента не меняется. У клиента в списке участников видно «Оплата ожидается». |
| PAYG-02 | Персональная запись без пакета | Повторить PAYG-01 для персонального слота и продукта `PERSONAL`. | Создана запись типа `PERSONAL` с ожидаемой оплатой; единственное место слота занято. |
| PAYG-03 | Запись по пакету не меняется | В том же слоте выбрать «По пакету» и клиента с подходящим пакетом. | Создаётся обычная запись с резервом посещения. Новая `Payment(EXPECTED)` не появляется; статус оплаты записи — «Не требуется». |
| PAYG-04 | Отображение долга | После PAYG-01 закрыть и вновь открыть слот. | У клиента сохраняется пометка «Оплата ожидается». У оплаты заполнены клиент, `bookingReferenceId`, название услуги-снимок и сумма на момент бронирования. |
| PAYG-05 | Подтверждение оплаты после посещения | Для записи из PAYG-01 установить `ATTENDED`, затем вызвать `POST /studio/bookings/confirm-pay-as-you-go-payment`, указав СБП, время и номер чека. | `Payment` становится `PAID`, сохраняются способ, время и номер чека; `Booking.paymentStatus` становится `PAID`. |
| PAYG-06 | Наличные и карта | Повторить PAYG-05 отдельно со способами «Наличные» и «Карта». | Оба способа сохраняются корректно; итог — `PAID`. |
| PAYG-07 | Повтор подтверждения | После PAYG-05 повторно выполнить команду подтверждения для той же записи. | Успешный идемпотентный ответ либо понятное отсутствие доступного действия; не создаётся вторая оплата, сумма и связи не меняются. |
| PAYG-08 | Нельзя оплатить до посещения | Для новой записи со статусом `BOOKED` открыть команду подтверждения оплаты и отправить форму. | Операция отклонена с сообщением, что оплату по факту можно подтвердить только после `ATTENDED`; статусы остаются `EXPECTED`. |
| PAYG-09 | Отмена будущего занятия | В слоте с неоплаченной записью выбрать «Отменить занятие» и подтвердить. | Запись получает `CANCELLED_BY_STUDIO`, ожидаемая оплата — `FAILED` с причиной отмены, `paymentStatus` записи — `WAIVED`. Заполненность слота становится 0. |
| PAYG-10 | Смешанный слот | В групповой слот добавить одного клиента по пакету и одного с оплатой по факту. Затем отменить слот. | У пакетной записи освобождается резерв посещения; у записи по факту закрывается ожидаемая оплата. Обе записи отменены, заполненность 0. |
| PAYG-10a | Вид задолженностей | После PAYG-01 открыть «Оплаты» → «К оплате». | В списке видна ожидаемая оплата с клиентом, услугой-снимком, суммой и ID записи. Оплаты `PAID`, `FAILED` и `REFUNDED` в этот вид не попадают. |
| PAYG-10b | Журнал создания занятия | Создать занятие из часовой сетки и открыть «Журнал событий студии». | Есть успешное событие `SESSION_CREATED` («Занятие создано») с ID созданного занятия. |
| PAYG-10c | Журнал записи и оплаты | Выполнить PAYG-01, затем PAYG-05; открыть «Журнал событий студии». | Есть успешные события `BOOKING_CREATED` с ID записи и `PAYMENT_CONFIRMED` с ID записи и оплаты. |

## Проверки валидации

| ID | Сценарий | Шаги | Ожидаемый результат |
| --- | --- | --- | --- |
| PAYG-11 | Нет подходящего продукта | Открыть слот, для формата которого отсутствует активный `SINGLE` или `PERSONAL`, выбрать «Оплата по факту». | Кнопка добавления недоступна; отображается «Нет подходящих разовых продуктов». |
| PAYG-12 | Несовпадение формата | Вызвать endpoint создания с продуктом другого формата, чем слот. | Ответ `409 PRODUCT_MISMATCH`; не создаются ни запись, ни оплата, вместимость не меняется. |
| PAYG-13 | Неактивный или пакетный продукт | Вызвать endpoint с неактивным продуктом или продуктом `GROUP_PACKAGE`. | Ответ `409 PRODUCT_NOT_BOOKABLE`; данные не меняются. |
| PAYG-14 | Прошедший слот | Вызвать endpoint для слота в прошлом. | Ответ `409 SESSION_IN_PAST`; запись и оплата отсутствуют. |
| PAYG-15 | Нет свободных мест | Заполнить слот до вместимости и попытаться создать запись с оплатой по факту. | Ответ `409 INSUFFICIENT_CAPACITY`; число участников и оплат не меняется. |
| PAYG-16 | Неверные обязательные данные | Отправить пустой client, product, slot или idempotency key. | Ответ `400 INVALID_INPUT`; никакие сущности не создаются. |
| PAYG-17 | Неверное время оплаты | Для проведённой записи отправить некорректный `paidAt`. | Ответ `400 INVALID_PAID_AT`; оплата остаётся `EXPECTED`. |

## Проверки целостности и повторов

| ID | Сценарий | Шаги | Ожидаемый результат |
| --- | --- | --- | --- |
| PAYG-18 | Повтор создания с тем же ключом | Дважды отправить создание с одинаковыми `personId`, `classSessionId`, `productId` и `idempotencyKey`. | Второй ответ помечен как duplicate; остаются одна запись и одна оплата, заполненность увеличена только на 1. |
| PAYG-19 | Повтор после обрыва клиента | Отправить создание, дождаться записи в CRM, затем повторить запрос с тем же ключом, имитируя потерю ответа. | Возвращается исходная запись и оплата; дубликатов нет. |
| PAYG-20 | Реквизиты оплаты | После PAYG-01 открыть созданную оплату. | У оплаты заполнены клиент, `bookingReferenceId`, `productNameSnapshot`, сумма и `EXPECTED`. Объектные связи с записью и продуктом не используются. |
| PAYG-21 | Изменение прайса | После PAYG-01 изменить цену продукта; затем подтвердить оплату ранее созданной записи. | Сумма в созданной оплате не меняется и равна цене на момент бронирования. |
| PAYG-22 | Защита от повторной операции | Повторить создание с тем же `idempotencyKey`. | Возвращается исходный результат, у записи остаётся одна финансовая обязанность. |

## Регрессия пакетов

1. Оформить пакет клиенту, создать по нему будущую запись и убедиться, что
   `visitsAvailable` уменьшается, а `visitsReserved` увеличивается.
2. Отменить эту запись и убедиться, что резерв освобождён, без появления
   `Payment(EXPECTED)`.
3. Внести прошедшее занятие через команду **«Внести прошедшее занятие»** и
   проверить `CONSUME` в журнале пакета.
4. Повторить PAYG-01 для того же клиента: его пакет не должен быть выбран или
   списан автоматически, если оператор явно выбрал «Оплата по факту».

## Результат прогона

Для каждого кейса зафиксировать ID записи, оплаты и слота, фактический статус,
время выполнения и скриншот календаря для PAYG-01, PAYG-05 и PAYG-09. Ошибки
вносить с телом ответа endpoint и этими ID — это позволит восстановить
состояние без поиска по имени клиента.
