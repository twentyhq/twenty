# Gelios — участники при создании тренировки

14 октября 2026. Подготовлено локально, на stage/production не применялось.

## Сверка с CRM

В class-schedule.front-component.tsx функции getMatchingMembership и saveSession подбирают ACTIVE пакет с visitsAvailable>0, активацией до занятия, действующим сроком, совпадающими product/sessionFormat. Создание CRM сначала сохраняет слот, затем добавляет pendingParticipants отдельными доменными командами.

Внешний UI использует тот же порядок и критерии, но выбирает конкретный пакет явно и сохраняет неизменяемый список участников для безопасного повтора.

## Форма

- «Доступный клиент» содержит только людей с подходящим пакетом на выбранную дату. Клиенты без подходящего пакета отсутствуют в выборе.
- Выбор конкретного пакета показывает название и остаток. Можно добавить человека в список и убрать из него до отправки — это локальный черновик, без записей CRM.
- Групповая тренировка: GROUP_PACKAGE, соответствующий sessionFormat, несколько разных клиентов в пределах вместимости.
- PERSONAL_EQUIPMENT: PERSONAL пакет, один клиент, вместимость 1 (readonly).
- При смене даты/формата пакеты пересчитываются; невалидный уже выбранный участник не списывается молча — сохранение блокируется до исправления.
- Будущее: BOOKED + RESERVE(-1), без фактического CONSUME.
- Прошедшее: выбранные люди явно считаются посетившими. Нужны подтверждение проведения и основание. Сервер выполняет preview всех выбранных посещений, затем ATTENDED + CONSUME(-1) каждому; длительность пакета должна совпасть с занятием.
- Пустое занятие не создаёт посещений/списаний. Для текущего ещё не закончившегося занятия и сплита пакетное добавление недоступно, используются отдельные действия.

## Контракт / восстановление

sessions/create принимает participants: [{personId,membershipId}] и attendanceReason (для прошедшего занятия с людьми). Pydantic проверяет UUID, CRM повторно проверяет владельца/формат/категорию/дату/остаток, дубли и вместимость до первого создания.

В classSessions добавлено nullable TEXT creationRequest (UUID поля 63a2073b-e68c-41df-b2ab-f1c6c43cd754): исходные status/participants/attendanceReason сохраняются вместе со слотом. Это фиксирует запрос даже при сбое записи SESSION_CREATED. Изменённый список с прежним ключом получает 409, не назначает новых людей.

Ключ каждого участника детерминирован: <ключ создания>:participant:<personId>. Повтор после частичного сбоя проходит уже созданных участников без второго резерва/списания, затем заканчивает оставшихся. SESSION_CREATED и BOOKING_CREATED обязательны; CONSUME/RESERVE пишутся штатными CRM-командами.

Это последовательная цепочка, не общая DB-транзакция: слот и часть участников могут уже сохраниться при ошибке. Не создавать новое занятие с новым ключом после такого отказа: сначала проверить карточку/журнал, повторить прежний запрос либо завершить разбор вручную. Лимиты concurrency из предыдущего этапа сохраняются.

66 API tests, 3 DB tests пропущены. 25 UI tests.
